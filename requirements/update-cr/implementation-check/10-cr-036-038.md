## CR-036

**Statement:** The Customer and Vehicle of interest boxes should work more like the boxes in the leads menu.

**Status:** implemented

**Place named:** The inventory does not name a page. The illustration is the Add Lead form (Customer, and Vehicle of interest) compared with the Leads page search. `07-workflows-and-ui.md` W14 says the screen is unknown and that the only controls with those labels are on `/leads`. A-20 asks which interaction to copy and does not answer it. The sentence asks that the boxes be similar to the leads menu; it does not name a second widget or a second page.

**Present:**

- The leads list filters in `LeadsPage` (`frontend/react/src/pages/LeadsPage.tsx`) are `SearchSuggest` boxes: placeholder "Customer name" (`filters.q`) and placeholder "Vehicle" (`filters.vehicle`). That is the leads menu search.
- Add lead (`FormDrawer` title "Add lead", `openCreate`) uses the same `SearchSuggest` control for both named boxes. Customer (`customerText`, aria-label "Customer") calls `suggestCustomers`, which calls `customersApi.list({ q, size: SUGGEST_LIMIT })`. Vehicle of interest (`vehicleText`, aria-label "Vehicle of interest", label "Vehicle of interest (in stock)") calls `suggestVehicles`, which calls `vehiclesApi.list({ q, status: 'IN_STOCK', size: SUGGEST_LIMIT })`. Picking a suggestion stores `customerId` or `vehicleId`. Changing the text clears that id until another suggestion is picked.
- `CustomerService.List` (`backend/dotnet/DealerOps.Core/Customer/CustomerService.cs`) matches `q` with `Name.Contains`, and also email and phone. `VehicleService.List` (`backend/dotnet/DealerOps.Core/Vehicle/VehicleService.cs`) matches `q` with `EF.Functions.Like` on VIN, make, model, and stock number, and applies `Status` when the client sends `IN_STOCK`.
- On an open lead, the edit drawer uses `SearchSuggest` for Vehicle of interest (`editVehicleText`). A closed lead shows that value in a disabled input.
- A search of `frontend/react/src` finds the label "Vehicle of interest" and the form label "Customer" only in `LeadsPage.tsx`. The table columns "Customer" and "Vehicle of interest" are display columns, not search boxes.

**Missing:** Nothing the sentence requires on the only screen that has those labels. The document does not describe a further interaction. The edit drawer does not offer a Customer search box; the customer is a link to `/crm?customerId=`. The add-form pickers store an id only when a suggestion is picked. They do not pass a free-text value on Enter, which the leads list search does. The CR does not ask the form to filter the lead list.

**Opened:** `frontend/react/src/pages/LeadsPage.tsx` (`LeadsPage`, `suggestCustomers`, `suggestVehicles`, `openCreate`, `customerText`, `vehicleText`, `editVehicleText`); `frontend/react/src/components/SearchSuggest.tsx` (`SearchSuggest`); `frontend/react/src/api/leads.ts` (`leadsApi.list`); `backend/dotnet/DealerOps.Core/Customer/CustomerService.cs` (`List`); `backend/dotnet/DealerOps.Core/Vehicle/VehicleService.cs` (`List`).

## CR-037

**Statement:** Searching team activity by user should return results for a partial name.

**Status:** implemented

**Place named:** Team activity user search. `03-modified-behavior.md` states the old behavior as no results on a partial user search, and the new behavior as those searches working with partial text. A-18 asks which fields and what minimum length; the code has no minimum length.

**Present:**

- `TeamPage` (`frontend/react/src/pages/TeamPage.tsx`) Activity tab renders `AuditLogPanel` with `load={auditApi.dealershipLog}`. `suggestActors` keeps members where `matchesAny(q, m.username, m.displayName)` and uses `value: m.username`. `members` comes from `membersApi.list()` inside `load`.
- `AuditLogPanel` (`frontend/react/src/components/AuditLogPanel.tsx`) binds the actor box (placeholder "Actor username") to `draft.actor`. Picking a suggestion, pressing Enter, or clicking Search copies that text into `filter` and reloads. `auditApi.dealershipLog` (`frontend/react/src/api/audit.ts`) sends it as `actor` on `GET /api/v1/dealer/audit`. The comment on `AuditLogFilter` says `actor` matches any part of the username, ignoring case.
- `AuditController.Dealership` (`backend/dotnet/DealerOps.Core/Audit/AuditController.cs`) binds `[FromQuery] AuditLogFilter` and calls `AuditService.ListDealership`. `AuditService.Filtered` (`backend/dotnet/DealerOps.Core/Audit/AuditService.cs`) trims `filter.Actor`, lowercases it, and keeps rows where `ActorUsername.ToLower().Contains(actor)`. `AuditLogFilter` (`backend/dotnet/DealerOps.Core/Audit/Dto/AuditLogFilter.cs`) documents the same rule. A fragment such as the start or the middle of a username matches. There is no exact-match comparison and no minimum length.
- `matchesAny` in `frontend/react/src/components/SearchSuggest.tsx` is a case-insensitive substring test, so the suggestion list also opens for a partial username or a partial display name. Picking a suggestion searches by that member's username, which the `Contains` filter returns.
- Gateway route `dealer-core-public` in `backend/dotnet/DealerOps.Gateway/appsettings.json` matches `/api/v1/{**catch-all}` and forwards to the core cluster. The route entry has no query transform.

**Missing:** Nothing the sentence requires for a partial username. The log query matches `ActorUsername` only. Typing a display name that is not part of the username and pressing Search, without picking the suggestion, does not match display name. The table does not reload on each keystroke; it reloads on pick, Enter, or Search. The CR does not ask for a live reload. Partial search of the admin audit log is a later item, not this one; the same `Filtered` method is what `ListPlatform` uses.

**Opened:** `frontend/react/src/pages/TeamPage.tsx` (`TeamPage`, `load`, `suggestActors`); `frontend/react/src/components/AuditLogPanel.tsx` (`AuditLogPanel`); `frontend/react/src/components/SearchSuggest.tsx` (`matchesAny`, `SearchSuggest`); `frontend/react/src/api/audit.ts` (`auditApi.dealershipLog`, `AuditLogFilter`); `frontend/react/src/api/members.ts` (`membersApi.list`, `memberLabel`); `backend/dotnet/DealerOps.Core/Audit/AuditController.cs` (`Dealership`); `backend/dotnet/DealerOps.Core/Audit/AuditService.cs` (`ListDealership`, `Filtered`); `backend/dotnet/DealerOps.Core/Audit/Dto/AuditLogFilter.cs` (`AuditLogFilter`); `backend/dotnet/DealerOps.Gateway/appsettings.json` (route `dealer-core-public`).

## CR-038

**Statement:** On the leads page, the owner field should start as the person creating the lead and remain changeable.

**Status:** implemented

**Place named:** Leads page, while creating a lead. `03-modified-behavior.md` and `07-workflows-and-ui.md` W15 step 1 say the same: on create, Owner starts as the creator and stays editable. A-20 asks whether a manager may create a lead whose owner starts as someone else; the sentence itself says the field starts as the creator and can be changed.

**Present:**

- `openCreate` in `LeadsPage` (`frontend/react/src/pages/LeadsPage.tsx`) sets `createForm.ownerUsername` to `session.username` from `useSessionStore`. The comment on that assignment says the creator owns a new lead by default and can change it. The same assignment runs for the Add lead button and for `/leads?newLeadFor=`, which calls `openCreate` with the loaded customer.
- The Add lead Owner control is a `select` bound to `createForm.ownerUsername`. It is not disabled. Options are "Unassigned" (`value=""`) plus every row from `owners`, loaded by `membersApi.list()`. `onChange` writes the chosen username back into `createForm`.
- `leadsApi.create` (`frontend/react/src/api/leads.ts`) posts `ownerUsername` via `blankToUndefined`. A non-blank username is sent. "Unassigned" omits the field.
- `LeadController.Create` (`backend/dotnet/DealerOps.Core/Lead/LeadController.cs`) accepts `CreateLeadRequest` and calls `LeadService.Create`. `Create` sets `OwnerUsername` from `TrimToNull(body.OwnerUsername)` after `RequireMember`. `RequireMember` allows null, and otherwise requires an active membership in the caller's dealership (`Memberships`, `Active`). Another member's username is accepted. The service does not overwrite the submitted owner with the caller.
- `MemberDirectoryController.List` (`backend/dotnet/DealerOps.Core/Dealer/MemberDirectoryController.cs`) returns `MemberDirectoryService.ActiveMembers`, which lists active members of the caller's dealership, including the signed-in member, so the prefilled username is one of the select options.
- On an open lead, the edit drawer Owner `select` stays enabled and can be changed, including to "Unassigned". A closed lead disables that select. That is the existing lead's owner, not a second default.

**Missing:** Nothing the sentence requires. The server does not invent an owner when `ownerUsername` is omitted; the prefill is the Add lead field. The leads list Owner filter is a separate filter and is not prefilled. The edit form does not replace the saved owner with the person who opens the lead.

**Opened:** `frontend/react/src/pages/LeadsPage.tsx` (`LeadsPage`, `openCreate`, `createForm`, `owners`); `frontend/react/src/store/session.ts` (`username`); `frontend/react/src/api/leads.ts` (`leadsApi.create`, `blankToUndefined`); `frontend/react/src/api/members.ts` (`membersApi.list`); `backend/dotnet/DealerOps.Core/Lead/LeadController.cs` (`Create`); `backend/dotnet/DealerOps.Core/Lead/LeadService.cs` (`Create`, `RequireMember`); `backend/dotnet/DealerOps.Core/Lead/Dto/CreateLeadRequest.cs` (`OwnerUsername`); `backend/dotnet/DealerOps.Core/Dealer/MemberDirectoryController.cs` (`List`); `backend/dotnet/DealerOps.Core/Dealer/MemberDirectoryService.cs` (`ActiveMembers`).
