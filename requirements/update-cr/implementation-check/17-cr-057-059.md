# Implementation check: CR-057–CR-059

Scope: active .NET 10 (`DealerOps.Core`, `DealerOps.Gateway`) and `frontend/react`. `DealerOps.AiService` has no pending-account or audit-log behavior. Java and Vue were not used.

Clarifying notes used from the analysis folder (not extra requirements): `02-new-capabilities.md` §6.3 and §5.2, `03-modified-behavior.md` (pending-account edit; platform audit log), `07-workflows-and-ui.md` W28 and W29, `08-api-and-integrations.md` §7.5 and §8, `09-gaps-risks-ambiguities.md` A-15 and A-18. Those notes say the target column order, the partial-match fields, and the day-picker label text are not specified.

## CR-057

- **Statement:** Admins must be able to edit a pending account's email, phone, and username when the creation details were entered incorrectly.
- **Status:** implemented
- **Place named:** Logged in as platform admin > pending accounts.

**Present**

- Admin → Pending accounts renders `PendingAccounts` (`frontend/react/src/pages/AdminPage.tsx`, tab `pending`). The same component is also mounted in the dealership staff drawer (`dealerId` set).
- Each row has Edit. `openEdit` / `saveEdit` open a dialog with username, login email, and login phone, and call `adminApi.updatePending` (`frontend/react/src/components/PendingAccounts.tsx`, `frontend/react/src/api/admin.ts` `UpdatePendingUserBody`).
- `PATCH /api/v1/admin/pending-users/{username}` is `AdminPendingUserController.Update`, which calls `MembershipService.UpdatePending`.
- `UpdatePending` requires the platform admin (`TenantGuard.RequireAdmin`), loads only an active dealer user with no active membership (`PendingAccount`), and writes username, email, and phone. `NewAccountRules.CanonicalContact` requires an email or a phone and normalizes both. `NewAccountRules.RequireAvailable` rejects a username, email, or phone already used by another account. A username change also rewrites that account's membership rows. The response is `PendingUserResponse` (username, display name, email, phone, created time, requested dealership).
- The gateway forwards `/api/v1/{**catch-all}` to Core (`backend/dotnet/DealerOps.Gateway/appsettings.json`, route `dealer-core-public`). A platform-admin token may call `/api/v1/admin` (`DealerOps.Gateway` `Program.cs` role gate).

**Missing**

- Nothing in the CR statement. Display name is shown and is not an edit field; the statement's examples are email, phone, and username only.
- The pending list requests one page of 10 (`adminApi.pendingUsers` size 10) and does not page further, so Edit is only on those rows. The update API itself is not limited to that page.

## CR-058

- **Statement:** The admin audit log should put search options and columns in the same order, and should be searchable by the change that was made.
- **Status:** implemented
- **Place:** Admin → Audit log (`AdminPage` tab `audit` renders `AuditLogPanel` with `load={auditApi.platformLog}` and `showDealer`).

**Present**

- `AuditLogPanel` comment and layout put the filters in this order: From date, To date, Actor username, Action, Record type, Dealership id (admin only), Search changes. Columns on the admin log are When, Actor, Action, Record, Dealership, Changes, Source IP (`frontend/react/src/components/AuditLogPanel.tsx`). From date and To date are the two controls for When. Actor, Action, Record, Dealership, and Changes then follow that same column order.
- Search changes is `draft.q`. `auditApi.platformLog` sends it as `q` (`frontend/react/src/api/audit.ts` `logParams`). `GET /api/v1/admin/audit` is `AuditController.Platform`, which calls `AuditService.ListPlatform` → `Filtered`.
- `AuditLogFilter.Q` is matched, case-insensitive, against action wire names, record-type wire names, `FieldSummary`, and `PreviousValues` (`AuditService.Filtered`). That is the stored change text (new and previous values), plus the action and record type.
- Password sign-in rows store `method` = `password` on `LOGIN`, and `LOGIN_FAILED` stores `method` and `reason` (values include `password`, `bad_password`, and `no_password`) in `AuthService.RecordLogin` / `LoginFailed`. The typed password and the typed identifier are not stored. A changes search for the word `password` therefore matches those stored summary fields.

**Missing**

- Nothing required by the statement. Source IP is a column after Changes and has no search control, so the two lists are not the same length. The analysis does not name a required sequence (`03-modified-behavior.md`; A-18). There is no Location column; that name belongs to the sortable-column notes, not to this statement.

## CR-059

- **Statement:** Admin audit-log search should match partial input, and its day pickers should be labeled.
- **Status:** implemented
- **Place:** Same admin audit log and the same `AuditLogPanel` (W11 and W29). Day-picker labeling is also CR-026; this check is only the admin log.

**Present**

- Actor text is not an exact username. `AuditService.Filtered` uses a case-insensitive `Contains` on `ActorUsername`. The actor box is `SearchSuggest`: Search, or Enter with no highlighted suggestion, applies the typed text (`onEnter` → `setFilter`). Picking a suggestion also applies it. Suggestions may match a member's display name, email, or phone (`AdminPage.suggestActors` / `suggestMembers`), but the value sent is a username.
- The changes box is also a substring match (`Filtered` on `Q`, described under CR-058). There is no minimum length beyond a non-blank string.
- Action and record type are dropdowns of full codes (`ACTIONS`, `ENTITY_TYPES`) and stay exact matches. A partial action or record-type word can still match through the changes box, because `Q` compares the text to those wire names.
- Day pickers are labeled. Each date input is wrapped in `<label className="filter-date">` with the visible text `From date` or `To date`, and an `aria` name is not used instead of that text. `.filters > .filter-date` lays the caption beside the input (`frontend/react/src/styles.css`). The analysis does not prescribe the words; these two labels are present.

**Missing**

- Nothing in the statement. A display name typed into the actor box and searched without picking a suggestion is matched only against `actor_username`, not against display name. The analysis leaves the partial-match fields unspecified (A-18) and infers a username substring (`08-api-and-integrations.md` §8.2), which is what `Filtered` does.
