# Implementation check: CR-060 through CR-062

Checked the active .NET 10 backend (`backend/dotnet/DealerOps.Core`, `backend/dotnet/DealerOps.Gateway`) and `frontend/react`. `DealerOps.AiService` has no dealership, user-delete, or account-contact routes. Java and Vue were not used.

Clarifying notes used only to place the screens: `requirements/update-cr/analysis/07-workflows-and-ui.md` (W30, W31) and `requirements/update-cr/analysis/02-new-capabilities.md` (§6.4, §6.5). The change document does not define the confirmation text, hard versus soft delete, or the cascade of vehicles and sales.

## CR-060

- **Status:** implemented
- **Statement:** A platform admin must be able to delete a dealership, and deletion must take at least one extra confirmation step.
- **Place named in the inventory:** Logged in as platform admin > Dealerships > Edit.

**Present**

- `DealerAdminService.Delete` (`backend/dotnet/DealerOps.Core/Dealer/DealerAdminService.cs`) is called by `AdminDealerController.Delete` (`DELETE api/v1/admin/dealers/{id}` in `backend/dotnet/DealerOps.Core/Dealer/AdminDealerController.cs`). `TenantGuard.RequireAdmin` (`backend/dotnet/DealerOps.Core/Common/Tenant/TenantGuard.cs`) allows only `AppRole.PlatformAdmin`.
- The delete is a soft delete. `DealerEntity.DeletedAt` is set, `Active` is set to false, active memberships are unbound, and a matching `RequestedDealerId` is cleared. `DealerAdminService.List` and `DealerAdminService.Load` omit rows whose `DeletedAt` is set, so the dealership leaves the admin list. `PublicDealerController.Dealers` lists only `Active` dealerships, so it also leaves the public directory. Vehicles, sales, customers, and audit rows are not removed; the method comment and the dialog copy both say that history is kept.
- The React admin calls `adminApi.deleteDealer` (`frontend/react/src/api/admin.ts`). On `AdminPage` (`frontend/react/src/pages/AdminPage.tsx`), the Dealerships row action `openDeleteDealer` opens a `ConfirmDialog`. `deleteDealer` runs only when the typed value equals `legalName` (`confirmDisabled` stays on until then). That typed-name dialog is the extra confirmation step.
- The gateway route `dealer-core-public` in `backend/dotnet/DealerOps.Gateway/appsettings.json` forwards `/api/v1/{**catch-all}` to core, with no method filter on that route.

**Missing**

- The named place is Dealerships > Edit. The Edit dealership `FormDrawer` in `AdminPage` has profile fields and Save. It has no Delete control. Delete is a row action on the Dealerships table, beside Edit and Staff.
- `DealerAdminService.Delete` does not call `NotificationService.ResolveByCorrelation`. That call is in `MembershipService.RetireLogin`, which this dealership delete does not use. The dialog copy says pending join requests are cancelled; the service clears `RequestedDealerId` and unbinds active members. This check did not open the notification list query, so it does not say whether an old join-request row stays visible.

## CR-061

- **Status:** implemented
- **Statement:** An admin must be able to delete a user, and deletion must take at least one extra confirmation step.
- **Who, from the same-paragraph note:** The inventory says "Admins" and does not name a screen. W31 places it on platform admin > Members. The code follows that: `TenantGuard.RequireAdmin` is platform admin only. A dealership manager has no delete-account route. `DealerTeamController.RemoveMember` unbinds staff; it does not delete the login.

**Present**

- `AdminMemberController.DeleteAccount` (`DELETE api/v1/admin/dealers/{id}/members/{username}/account` in `backend/dotnet/DealerOps.Core/Dealer/AdminMemberController.cs`) calls `MembershipService.DeleteAccount`.
- `DeleteAccount` refuses a platform-admin login, including the caller. Otherwise it deactivates every active membership, then `RetireLogin` sets the user inactive, clears dealership and join-request fields, and suffixes email, phone, and Google subject with `:deleted:{id}`. The username and audit row stay. `MembershipService.List` then hides that user (`User.Active` must be true).
- On the Members tab of `AdminPage`, `openDeleteAccount` opens a `ConfirmDialog`. `deleteAccount` calls `adminApi.deleteMemberAccount` only after the typed value equals the username.
- Accounts with no active membership are a separate path, `AdminPendingUserController.Delete` → `MembershipService.DeletePending`, used by `PendingAccounts` (`frontend/react/src/components/PendingAccounts.tsx`). That dialog is one extra confirm (Cancel / Delete) and does not require a typed username. It still meets "at least one extra step." The pending-account remove request is a different inventory item; it is listed here only because it also deletes a user login.

**Missing**

- The staff drawer in `AdminPage` (`openMembers`) can Unbind an active member. It does not offer Delete account or Edit contact. Those actions are on the Members tab, which loads the same memberships through `loadFlatMembers`.
- Nothing in this CR requires a hard delete. The code does not remove the `app_user` row.

## CR-062

- **Status:** implemented
- **Statement:** An admin must be able to edit some account information, such as email or phone number.
- **Scope note:** This sentence is the same source paragraph as CR-061. W31 reads the examples as email or phone on platform admin > Members, not every account field. Pending-account edit (username, email, and phone) is the earlier pending-account item; it is a second path, not the only one.

**Present**

- `AdminMemberController.UpdateContact` (`PATCH api/v1/admin/dealers/{id}/members/{username}`) takes `PatchMemberContactRequest` (`Email`, `Phone`) and calls `MembershipService.UpdateContact`. The caller must be the platform admin. The method comment says the target may be an active or unbound member still listed for that dealership. `UpdateContact` canonicalizes the contact, checks uniqueness, writes email and phone, and audits `APP_USER` / `UPDATE`.
- `AdminPage` Members column "Account" has Edit contact. `openContact` / `saveContact` send `adminApi.updateMemberContact`. The dialog fields are login email and login phone. Save is blocked in the page when both are blank, matching the request comment that at least one of the two is required and a blank value clears that one field.
- Pending accounts: `AdminPendingUserController.Update` → `MembershipService.UpdatePending`, and `PendingAccounts` edits username, email, and phone. That covers email and phone for logins that are not listed as members.

**Missing**

- On the member path, the dialog does not edit username or display name. The statement's examples are email and phone, and both are on that dialog.
- A dealership manager can edit another member's full name and phone through `DealerTeamController.PatchMember` and `PatchMemberRequest` (`DisplayName`, `Phone` only), and `TeamPage` shows those two fields. That route does not edit email, and the actor is a manager, not the platform admin named for this paragraph.
