# Implementation check: CR-021 through CR-024

Thread 6 of 20. Read-only check of the active .NET 10 backend (`DealerOps.Core`, `DealerOps.Gateway`) and `frontend/react`. `DealerOps.AiService` was not opened; these four items do not call it. Java and Vue were not inspected.

Clarifying notes used only for these four items: `07-workflows-and-ui.md` W8 and W9, `08-api-and-integrations.md` §6.4 and §7.2, `09-gaps-risks-ambiguities.md` A-14, `10-design-and-code-impact.md` §7 and §8. ## CR-021

**Statement:** An account must still be creatable when the full name is already used.

**Status:** implemented

**Places named:** Home-page create account; platform admin > Dealerships > Staff > create a staff account; any signed-in account > Profile. The source says other places may exist.

**Present:**

- `NewAccountRules.RequireAvailable` (`backend/dotnet/DealerOps.Core/Dealer/NewAccountRules.cs`) rejects only a taken username, email, or phone. The class comment says the full name is not unique. `Conflict` maps only `uk_user_username`, `uk_app_user_email`, and `uk_app_user_phone`.
- `AppDbContext.ConfigureDealer` (`backend/dotnet/DealerOps.Core/Data/AppDbContext.cs`) unique-indexes `Username`, `Email`, and `Phone` on `AppUserEntity`. There is no unique index on `DisplayName`. `AppUserEntity.DisplayName` is a required 120-character column and nothing else.
- Startup schema repair in `Program.cs` runs `ALTER TABLE app_user DROP INDEX uk_app_user_display_name` and comments that full names are no longer unique. `ErrorCode` (`backend/dotnet/DealerOps.Core/Common/Exceptions/ErrorCode.cs`) has `UsernameTaken`, `EmailTaken`, and `PhoneTaken`, and no display-name code.
- Home-page path that still creates an account: `LandingPage` (`frontend/react/src/pages/LandingPage.tsx`) links sample ads to `/register` (“Sign up to check your own ads”). `RegisterPage` posts `displayName` through `register`. Client checks are empty and length only. `TAKEN_FIELD` maps `USERNAME_TAKEN`, `EMAIL_TAKEN`, and `PHONE_TAKEN`. `AuthService.Register` trims `DisplayName`, calls `RequireAvailable(username, contact)`, and stores the name. `FirebaseSignIn` does the same. `GoogleDisplayName` keeps the Google name as entered; its comment says full names are not unique, so no numeric suffix is added.
- Admin staff create: `AdminPage.bind` (`frontend/react/src/pages/AdminPage.tsx`) requires a non-empty full name and calls `adminApi.bind`. `TAKEN_HINTS` covers username, email, and phone. `MembershipService.Add` and `RequestJoin` set `DisplayName` from the body and call `RequireAvailable` only for username, email, and phone.
- Profile: `ProfilePage.onSave` calls `patchMe` with `displayName`. `MeController.PatchMe` assigns the trimmed name and checks phone uniqueness against other rows only. The method comment says the full name is not unique.
- An extra place the source said might exist: a manager editing another member. `MembershipService.UpdateInOwnDealership` and the Team member drawer (`TeamPage`, label “Full name”) save `DisplayName` with a phone check only.

**Missing:** Nothing the statement requires. Username, email, and phone stay unique. The home header offers Sign in; the remaining home create path is the sample-ad link to `/register`, and that path does not reject a used full name. `AuthService.Register`’s exception comment still lists display name among field conflicts; the method does not check it.

`DealerOps.Gateway` has no display-name uniqueness check.

## CR-022

**Statement:** Menus that hold unsaved data or accept changes must confirm before those changes are lost or saved.

**Status:** partial

**Places named:** Platform admin > Dealerships > Edit; any dealership user > DMS > Add vehicle and Edit; CRM > Add customer and Edit; Leads > Add lead and Edit. `09-gaps-risks-ambiguities.md` A-14 says the source does not say whether each screen should warn on leave, ask before save, or message after save. The inventory statement covers both loss and save. Dealership-profile save and lead close are CR-023 and CR-024.

**Present:**

- `FormDrawer` (`frontend/react/src/components/FormDrawer.tsx`) takes `dirty`. Overlay click, the close button, and Escape call `requestClose`. When `dirty` is true that opens `ConfirmDialog` titled “Unsaved changes”, message `DISCARD_MESSAGE` (“Discard unsaved changes?”), confirm label “Discard”. Cancel stays in the form. `useLeaveWarning` (`frontend/react/src/components/unsavedChanges.ts`) while the drawer is open and dirty blocks tab close or reload (`beforeunload`) and asks `window.confirm` with the same message before an in-app `<a href>` click.
- `useFormBaseline` marks the form dirty only after `reset` and only when the current value’s JSON differs from that baseline.
- Dealership edit: `AdminPage.openEdit` resets `dealerBaseline`, and the edit drawer is `dirty={dealerBaseline.dirty}`. The same drawer is used for New dealership.
- Vehicle add and edit: `DmsPage` resets `vehicleBaseline` for a blank form and for a loaded vehicle, and the drawer is `dirty={vehicleBaseline.dirty}`.
- Customer add and edit: `CrmPage` resets `customerBaseline` the same way, and the drawer is `dirty={customerBaseline.dirty}`.
- Lead add and edit: `LeadsPage.openCreate` resets `createBaseline`. `fillEdit` resets `editBaseline`. The add drawer uses `createBaseline.dirty`. The open-lead drawer uses `editBaseline.dirty || noteText.trim() !== ''`.

**Missing:**

- None of those four saves asks before an ordinary commit. `AdminPage.createDealer` runs on Save / Create. `DmsPage.save` writes the vehicle immediately. `CrmPage.save` asks only when `customersApi.duplicates` finds a matching customer (a different change). `LeadsPage.create` / `submitCreate` asks only for that same duplicate-customer case. `LeadsPage.saveDetail` asks only when the stage is Won or Lost (CR-024); other lead edits save immediately.
- A-14 is unresolved, so a discard prompt alone does not meet the inventory sentence “before those changes are lost or saved.”
- Two other editors opened while reading these screens do not pass `dirty`: the staff-account `FormDrawer` in `AdminPage`, and the member-edit `FormDrawer` in `TeamPage`. The source says the menu list is incomplete. Those two were not in the named list.

`useLeaveWarning` does not hook browser Back. Drawer close on the four named menus is the path that uses `ConfirmDialog`.

## CR-023

**Statement:** Saving the dealership profile must require confirmation because it is a larger change.

**Status:** implemented

**Place named:** Manager > Team > Dealership profile (`TeamPage` in `frontend/react/src/pages/TeamPage.tsx`). `/team` is behind `ManagerGuard` (`frontend/react/src/router.tsx`). `DealerAdminService.PatchOwn` calls `TenantGuard.RequireManager`.

**Present:**

- The profile tab is a form whose submit handler is `requestProfileSave`. That sets `confirmProfileSave` and does not call the API.
- `ConfirmDialog` title “Save dealership profile”, message “Save changes to the dealership profile?”, confirm label “Save”. Confirm calls `saveProfile`, which calls `teamApi.saveProfile` and then `DealerTeamController.PatchProfile` (`PATCH /api/v1/dealer/profile`). Cancel only clears the flag.
- The dialog opens on every Save click while a profile is loaded and a save is not already running, including when the fields are unchanged.
- `useLeaveWarning(profileBaseline.dirty)` also asks before a link click or tab close while the loaded profile differs from `profileBaseline`.

**Missing:** Nothing the statement requires. The confirm is in the page; the API does not add a second check. Switching Team tabs does not discard the in-memory profile, because `dealer` lives on `TeamPage`, not inside the tab panel.

## CR-024

**Statement:** Closing a lead must be confirmed before it is saved.

**Status:** implemented

**Place named:** Any dealership user > Leads > Open (`LeadsPage` detail drawer).

**Present:**

- `isClosedStage` (`frontend/react/src/api/leads.ts`) is true for `WON` and `LOST`.
- `saveDetail` refuses a Lost stage with an empty `lostReason` (“A lost lead needs a reason”) before any dialog. If the edited stage is closed and `confirmClose` is false, it sets `confirmClose` and returns without calling `leadsApi.update`.
- `ConfirmDialog` title “Close lead”, message “Close this lead as {stage}? Won and lost leads are locked until someone reopens them.”, confirm label “Close lead”. Confirm calls `saveDetail` again, which then patches stage, owner, follow-up, vehicle, and lost reason. Cancel sets `confirmClose` back to false and does not save.
- The Save button is rendered only while `selected.stage` is still open (`!isClosedStage(selected.stage)`). A lead that is already Won or Lost shows Reopen instead. `reopen` does not use this dialog.

**Missing:** Nothing on the named screen. Selling a vehicle is a different action: `DmsPage` confirms the sale (“Confirm sale”), and `VehicleService.CloseLeadsForSale` then sets that vehicle’s open leads to Won or Lost with no separate lead-close dialog. That path is not Leads > Open.
