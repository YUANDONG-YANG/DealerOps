## CR-054

**Statement:** Creating a dealership staff account with invalid username characters must return an error that is easy to read.

**Status:** implemented

**Place named:** Logged in as platform admin > Dealerships > Staff (`AdminPage` staff drawer in `frontend/react/src/pages/AdminPage.tsx`). The source does not give the replacement sentence or the allowed characters. W26 says the desired text is not supplied and that a `400 VALIDATION` `fieldErrors` message on the username field is enough.

**Present:**

- Staff create posts through `adminApi.bind` (`frontend/react/src/api/admin.ts`) to `POST /api/v1/admin/dealers/{id}/members`. `AdminPage.bind` sends the username. It checks only that the username is non-empty (`"Enter a username."`) before the call. Character rules are not checked in the browser on this form.
- `CreateMemberRequest.Username` (`backend/dotnet/DealerOps.Core/Dealer/Dto/CreateMemberRequest.cs`) uses `[RegularExpression(@"(?=.*[A-Za-z])[A-Za-z0-9._-]{3,64}", ErrorMessage = "Username must be 3-64 characters: letters, digits, dot, underscore or hyphen, with at least one letter.")]`.
- `Program.InvalidModelStateResponseFactory` (`backend/dotnet/DealerOps.Core/Program.cs`) returns `400` with `ErrorBody` (`backend/dotnet/DealerOps.Core/Common/ErrorBody.cs`): code `VALIDATION`, message `"Validation failed."`, and `fieldErrors`. `PublicFieldError` keeps that `ErrorMessage`. It replaces a message only when the binder attached an exception or the text contains `Path:` or `DealerOps.`. The username sentence matches none of those, so the regex pattern is not sent.
- `AdminPage.bind` reads `fieldErrorsOf` (`frontend/react/src/api/http.ts`) and stores them in `memberErrors`. The staff drawer renders `memberErrors.username` in `form-error` under the Username input. The drawer banner is `Fix: Username — see the messages under each field.` A taken username (`409`) also gets `TAKEN_HINTS.username`; that hint is separate from the character error.

**Missing:** Nothing the statement requires. The source does not supply the new sentence; the code uses the English character rule above. The staff form does not repeat the rule before submit. `RegisterPage` (`frontend/react/src/pages/RegisterPage.tsx`) does, with `USERNAME_RX` and the sentence `"Use 3–64 letters, digits, dots, dashes or underscores, with at least one letter."` That page is public registration, not the staff drawer this item names.

## CR-055

**Statement:** A platform admin must not bind an account directly to a dealership, and may only send that dealership a join request.

**Status:** partial

**Place named:** The inventory line does not name a screen. W27 places it on Admin > Pending accounts and Admin > Dealerships > Staff. The stated reason is that a platform admin must not create an account and then use it to open a dealership’s customer and vehicle data. A-09 leaves open what happens for a dealership that has no manager yet. The code answers that case by still binding.

**Present:**

- `AdminMemberController.Add` (`backend/dotnet/DealerOps.Core/Dealer/AdminMemberController.cs`) calls `MembershipService.Add`. The comment on `Add` says a login is bound directly while the dealership has no active manager, and a join request is filed after that.
- When `Memberships` already has an active `DealerRole.Manager` for that dealership, `Add` returns `RequestJoin` and does not insert a membership. `AdminMemberController.Add` responds `202` with `JoinRequestSentResponse` (`backend/dotnet/DealerOps.Core/Dealer/Dto/AddMemberResult.cs`).
- `RequestJoin` creates the login when the username is new (including `PasswordHash` from the admin’s temporary password), leaves `DealerId` unset, and calls `JoinRequestService.SetRequested` (`backend/dotnet/DealerOps.Core/Dealer/JoinRequestService.cs`). `SetRequested` sets `RequestedDealerId` and `Notify` creates a `JOIN_REQUEST` notification. The response message is `MembershipService.JoinRequestSentMessage`: `"Join request sent to the dealership. A manager approves it in Team > Join Requests."`
- `AdminPage.bind` and `PendingAccounts.bindPending` (`frontend/react/src/components/PendingAccounts.tsx`) use `isJoinRequestSent`. On a join-request body they show that message. A pending row then shows `Join request sent to {name}`. The staff drawer copy says the same split: first manager is bound; otherwise a join request is sent.
- The platform-admin role still cannot call business routes. `DealerOps.Gateway` `Program.cs` rejects an admin token on any `/api/v1/` path that does not start with `/api/v1/admin` (comment AUTH-08). That gate does not stop a `Dealer.User` session.

**Missing:**

- Direct bind remains when the dealership has no active manager. `MembershipService.Add` sets the membership `Active = true` and `DealerRole = Manager`, sets the user’s `DealerId`, and `AdminMemberController.Add` returns `201` with `MemberResponse`.
- The staff drawer button is still `Create and bind`. Success copy is `{username} is bound as the dealership's first manager.` `PendingAccounts.rowActions` is still `Bind without password`, and a `201` uses the same first-manager sentence. `AdminPage.setStatus` reactivates by calling `adminApi.bind` again, so that path can bind directly too.
- The stated security outcome is not closed. `RequestJoin` still stores the password the admin typed. `AdminMemberController.ResetPassword` still sets a new password for an active member. Either one is a dealer-user login the admin can use after the account is in the dealership. The statement’s required behavior is “do not bind; only send a join request,” and that behavior is only the post-manager branch.

## CR-056

**Statement:** Admins must be able to remove pending accounts.

**Status:** implemented

**Place named:** The inventory line does not name a screen. W28 places it on Admin > Pending accounts, including the pending list inside the dealership staff drawer. The source does not require a second confirm and does not say hard delete. §7.5 infers the same soft delete as self-delete. The code does that, and the screen adds a confirm the source does not require.

**Present:**

- `PendingAccounts` is mounted from `AdminPage` on the Pending accounts tab and inside the staff drawer (`dealerId` set). Each row has `Delete`. `ConfirmDialog` title `Delete pending account` asks the admin to confirm. `confirmDelete` calls `adminApi.deletePending`, which is `DELETE /api/v1/admin/pending-users/{username}`.
- `AdminPendingUserController.Delete` (`backend/dotnet/DealerOps.Core/Dealer/AdminPendingUserController.cs`) calls `MembershipService.DeletePending` and returns `204`.
- `DeletePending` calls `TenantGuard.RequireAdmin` (`backend/dotnet/DealerOps.Core/Common/Tenant/TenantGuard.cs`), so the caller must be `Platform.Admin`. `PendingAccount` loads an active `Dealer.User` with no active membership, or throws `Pending account not found.`
- `RetireLogin` cancels a pending `JOIN_REQUEST`, sets `Active` false, clears `DealerId` and `RequestedDealerId`, and appends `:deleted:{id}` to email, phone, and Google subject. The username row and an `APP_USER` `DELETE` audit row stay. `Pending` lists only active dealer users with no active membership, so the removed account leaves the queue.
- `DealerOps.Gateway` `appsettings.json` proxies `/api/v1/{**catch-all}` to core. The admin business-route gate does not block `/api/v1/admin`.

**Missing:** Nothing the statement requires. `PendingAccounts` calls `adminApi.pendingUsers()` once. That client sends `size` 10 and the component has no pager and does not pass `q`, so only the first page of pending accounts is shown. A pending account past that page has no Delete control on this screen. `DeletePending` itself is not limited to that page.
