## CR-051

**Statement:** A lead for the same customer and the same vehicle must not be creatable twice.

**Status:** partial

**Place named:** Not named. `07-workflows-and-ui.md` W23 places the check on Leads create. The same note says the document does not say whether a closed lead still counts as a duplicate.

**Present:**

- `LeadService.RequireNoOpenDuplicate` (`backend/dotnet/DealerOps.Core/Lead/LeadService.cs`) rejects a lead when the same dealership already has a lead for that `customerId` and `vehicleId` whose stage is not `LeadStage.Won` or `LeadStage.Lost`. A null `vehicleId` returns without a check. The thrown code is `ErrorCode.LeadDuplicate` (wire `LEAD_DUPLICATE`, HTTP 409) with the message "This customer already has an open lead for this vehicle."
- `LeadService.Create` calls that check when `CreateLeadRequest.CustomerId` is set, before the lead row is inserted. A create that sends `NewCustomer` instead of `CustomerId` inserts a new customer first, so that path has no prior lead for that new id.
- `LeadService.Patch` calls it when the vehicle changes and the lead stays open. The comment there says a close frees the pair.
- `LeadService.Reopen` calls it before a closed lead is moved back to an open stage.
- `ErrorCode.LeadDuplicate` is defined in `backend/dotnet/DealerOps.Core/Common/Exceptions/ErrorCode.cs` and maps to 409.
- `LeadsPage.mapWrite` (`frontend/react/src/pages/LeadsPage.tsx`) turns `LEAD_DUPLICATE` into "This customer already has an open lead for this vehicle. Open that lead instead of adding another." `submitCreate` shows that string in `createError`. The same sentence is in `describeError`'s map in `frontend/react/src/api/errors.ts`. `leadsApi.create` posts to `POST /api/v1/leads` (`frontend/react/src/api/leads.ts`). The Leads page is the only React caller of `leadsApi.create`.

**Missing:**

- A won or lost lead for the same customer and vehicle does not block `Create`. The statement says the lead must not be creatable twice and does not exempt a closed lead.
- `BuyerSiteService.Inquire` (`backend/dotnet/DealerOps.Core/BuyerSite/BuyerSiteService.cs`) is the other `new LeadEntity` writer in Core. It matches a customer by phone, then always inserts a `LeadStage.New` lead on that vehicle. It does not call `RequireNoOpenDuplicate`, so a second open lead for that customer and vehicle can still be created from the buyer site.
- `AppDbContext.ConfigureLead` (`backend/dotnet/DealerOps.Core/Data/AppDbContext.cs`) indexes `(DealerId, Stage)` as `idx_lead_dealer_stage`. It does not unique `(dealer, customer, vehicle)`. The staff check is a query before insert, outside the create transaction, so two concurrent creates can both pass it.

## CR-052

**Statement:** When a vehicle is sold to a customer, leads tied to that sale should close automatically and receive the appropriate label.

**Status:** partial

**Place named:** Not named. The inventory source says the label is applied to the customers tied to the lead, and that the document does not name the label. `03-modified-behavior.md` repeats that the label is on those customers, and that the document does not say what happens for a buyer entered as Other. `09-gaps-risks-ambiguities.md` A-08 asks whether the closed thing is the lead or the customer, which leads, and which label.

**Present:**

- `VehicleService.Sell` (`backend/dotnet/DealerOps.Core/Vehicle/VehicleService.cs`) sells the vehicle, and in the same transaction calls `CloseLeadsForSale`.
- `CloseLeadsForSale` loads open leads for that `vehicleId` and dealership (`Stage` not `Won` and not `Lost`). When `lead.CustomerId` equals the CRM `buyerCustomerId`, the stage becomes `LeadStage.Won` and `LostReason` is cleared. Every other open lead on that vehicle becomes `LeadStage.Lost` with `LostReason` "Vehicle sold". Each change is audited as a lead `UPDATE`. The method comment calls this L6.
- The buyer is a CRM customer (`SellVehicleRequest` buyer id) or Other with a typed name. `CustomerEntity` is not updated in this method. When the buyer id is null, no lead's customer matches, so every open lead on the vehicle is marked Lost.
- `DmsPage.sell` (`frontend/react/src/pages/DmsPage.tsx`) posts the sale through `vehiclesApi.sell` (`frontend/react/src/api/vehicles.ts`), which comments that the call closes the vehicle's open leads. The Leads table shows the stage with `stageLabel` (`frontend/react/src/api/leads.ts`): `WON` is "Won" and `LOST` is "Lost". `LeadStage` (`backend/dotnet/DealerOps.Core/Lead/LeadStage.cs`) is `New`, `Contacted`, `Qualified`, `Won`, `Lost`.

**Missing:**

- No label is stored on the customer. `CustomerEntity` (`backend/dotnet/DealerOps.Core/Customer/CustomerEntity.cs`) has name, email, phone, address, and notes. `CloseLeadsForSale` writes only the lead's `Stage` and `LostReason`. The source sentence applies the label to the customers tied to the lead. The label name is not in the document, so Won and Lost are the code's choice, not a named requirement.
- Leads that are already Won or Lost are left unchanged. Leads with no vehicle, or a different vehicle, are not closed.
- A sale whose buyer is Other (no customer id) still closes every open lead on the vehicle as Lost. The analysis says the document does not say that Other closes leads.

## CR-053

**Statement:** The display-name field should be labeled as full name on Profile and on the admin staff-account form.

**Status:** implemented

**Place named:** Profile, and the admin page when creating a staff account. `08-api-and-integrations.md` says the visible label changes and the JSON field stays `displayName`.

**Present:**

- `ProfilePage` (`frontend/react/src/pages/ProfilePage.tsx`) labels the edit field `htmlFor="displayName"` as "Full name". The input is bound to the `displayName` state and saved as `displayName` on the profile patch. The account card shows the name value and does not use the words "display name".
- The staff drawer in `AdminPage` (`frontend/react/src/pages/AdminPage.tsx`) labels the create field "Full name". The input is `member.displayName`. Empty input sets `missing.displayName` to "Enter the full name." `FIELD_LABELS.displayName` is "Full name", so a field error for that property uses that label. The create body still sends `displayName`.

**Missing:** Nothing the statement requires. The staff list column header in that drawer is "Name", which is the table, not the create field. The stored property name remains `displayName`.
