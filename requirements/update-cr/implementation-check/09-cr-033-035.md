## CR-033

**Statement:** The model-year dropdown should list only years that fit the selected vehicle, or only common vehicles if doing this for every vehicle is too hard.

**Status:** implemented

**Place named:** Add Vehicle form, Model year field (the inventory illustration). `07-workflows-and-ui.md` W13 places the same control on the DMS Add vehicle drawer. The source allows a common-vehicle fallback and does not define “common.”

**Present:**

- `DmsPage` in `frontend/react/src/pages/DmsPage.tsx` builds `formYearOptions` with `modelYearsFor(form.make, form.model, yearOptions)` and renders that list in the Model year `select` (`purchaseFields` key `modelYear`). The same drawer is titled “Add vehicle” or “Edit vehicle.”
- `yearOptions` in `DmsPage.tsx` is every year from the next calendar year down through 1900.
- `modelYearsFor` in `frontend/react/src/vehicleRules.ts` looks up `MODEL_YEARS` by uppercased `make|model`. A listed pair keeps only years from its first production year through its last year, or through the `yearOptions` cap when no last year is stored. An unlisted pair returns `yearOptions` unchanged.
- `MODEL_YEARS` is a fixed client table of 61 make/model pairs (Toyota, Honda, Ford, Chevrolet, Nissan, Hyundai, Kia, Mazda, Subaru, Tesla, Jeep, Ram, GMC, Dodge, Volkswagen). A few pairs store an end year (`HONDA|FIT`, `FORD|EDGE`, `FORD|FOCUS`, `FORD|FUSION`, `CHEVROLET|CRUZE`, `CHEVROLET|BOLT EV`, `DODGE|GRAND CARAVAN`). The comment on `modelYearsFor` calls this the common-pair path.
- If the stored year is outside `formYearOptions`, the select adds that one year as an extra option so the current value still displays.
- `VehicleCatalogController` (`backend/dotnet/DealerOps.Core/Catalog/VehicleCatalogController.cs`) exposes `Makes`, `Models`, and `DecodeVin`. It does not return a year list for a make and model. `DmsPage` uses `catalogApi.makes` and `catalogApi.models` for the make and model controls only.

**Missing:** Nothing the statement requires once the allowed fallback is used. A year list for every make and model is not present. Pairs absent from `MODEL_YEARS`, including makes that appear in `POPULAR_MAKES` but have no rows in `MODEL_YEARS` (BMW, Mercedes-Benz, Audi, Lexus), still show 1900 through the next calendar year. The span is every integer year in the stored range, not a catalog of years the model was actually offered.

## CR-034

**Statement:** The VIN box should be moved to the top.

**Status:** implemented

**Place named:** The inventory sentence follows the Add Vehicle model-year note and does not repeat a page. `03-modified-behavior.md` and `07-workflows-and-ui.md` W13 step 6 read it as the top of the add-vehicle form. “The top” is not tied to a named section.

**Present:**

- `purchaseFields` in `DmsPage` (`frontend/react/src/pages/DmsPage.tsx`) is ordered VIN, Make, Model, Model year, then purchase cost, added on, repair cost, and Carfax URL. The comment above the array says VIN is first.
- `FormDrawer` (“Add vehicle” / “Edit vehicle”) maps `purchaseFields` before Source, Condition, Body type, and `detailFields`. VIN is the first control in that form.
- On create (`!edit`), the VIN row also shows a Decode button. On edit, the VIN input stays in the same first position and the Decode button is not rendered.

**Missing:** Nothing the statement requires. The public landing-page VIN decoder (`LandingPage.tsx`) is a separate preview and is not the Add Vehicle box named by the surrounding sentences.

## CR-035

**Statement:** There should be a box to search for vehicles that have open work orders.

**Status:** implemented

**Place named:** The inventory does not name a page. The sentence is the second half of the VIN-box sentence. `02-new-capabilities.md` §5.4 and `07-workflows-and-ui.md` W13 step 7 read it as a DMS search that limits the vehicle list to vehicles with open work orders. The control type (checkbox versus a count) is not stated.

**Present:**

- The DMS filter row in `DmsPage` (`frontend/react/src/pages/DmsPage.tsx`) has a checkbox labeled “Open work orders only”, bound to `filters.openWorkOrdersOnly`. Checking it calls `changeFilter`, which updates `filters` and resets to page 0. `load` depends on `filters` and calls `vehiclesApi.list`.
- `vehiclesApi.list` in `frontend/react/src/api/vehicles.ts` sends `openWorkOrdersOnly=true` on `GET /api/v1/vehicles` when that flag is set.
- `VehicleController.List` (`backend/dotnet/DealerOps.Core/Vehicle/VehicleController.cs`) takes `[FromQuery] bool openWorkOrdersOnly` and passes it on `VehicleFilter` (`backend/dotnet/DealerOps.Core/Vehicle/Dto/VehicleFilter.cs`).
- `VehicleService.List` (`backend/dotnet/DealerOps.Core/Vehicle/VehicleService.cs`) applies the flag by keeping vehicles that have at least one work order in `WorkOrderStatus.Open` or `WorkOrderStatus.InProgress` (`backend/dotnet/DealerOps.Core/WorkOrder/WorkOrderStatus.cs`) for the same vehicle and dealership. `Done` and `Cancelled` do not match.
- The same list already shows the count in the “Open WOs” column (`row.openWorkOrders`). That column is the count, not the search control.
- Gateway route `dealer-core-public` in `backend/dotnet/DealerOps.Gateway/appsettings.json` matches `/api/v1/{**catch-all}` and does not declare a query transform, so the query string is forwarded with the proxied request.
- `dealer-platform/openapi.yaml` `listVehicles` documents `openWorkOrdersOnly` as a boolean that, when true, returns only vehicles with at least one OPEN or IN_PROGRESS work order.

**Missing:** Nothing the statement requires. The document does not say whether the control is a checkbox or a number. The code uses a yes/no checkbox, not a box that searches by open-work-order count. The filter is on the DMS list, not inside the Add vehicle drawer.
