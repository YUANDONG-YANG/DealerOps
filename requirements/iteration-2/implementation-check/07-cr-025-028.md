## CR-025

**Statement:** Join requests should be split into a table of requests awaiting approval or rejection and a table of past approved or rejected requests.

**Status:** implemented

**Place named:** Logged in as any manager account > Team > Join requests (`TeamPage` in `frontend/react/src/pages/TeamPage.tsx`).

**Present:**

- The Join requests tab loads `notificationsApi.list(true)` (`frontend/react/src/api/notifications.ts`), which calls `GET /api/v1/dealer/notifications?includeResolved=true`.
- `NotificationService.List` (`backend/dotnet/DealerOps.Core/Notifications/NotificationService.cs`) returns resolved rows when `includeResolved` is true, and still limits `JOIN_REQUEST` rows to managers.
- `TeamPage` keeps only `kind === 'JOIN_REQUEST'` rows (`isJoinRequest`). `pendingSort` is `resolvedAt == null`. `historySort` is `resolvedAt != null`.
- When any join request exists, the tab renders two tables. “Pending” (`aria-label` “Pending join requests”) has Name, Email, Username, Source, Requested, and Actions. Actions call `joinRequestsApi.approve` / `reject`. “History” (`aria-label` “Join request history”) has the same identity columns plus Status and Resolved (`resolvedAt` and `resolvedBy`). History pages at 10 rows.
- `JoinRequestService.Approve` and `Reject` (`backend/dotnet/DealerOps.Core/Dealer/JoinRequestService.cs`) resolve the notification with `APPROVED` or `REJECTED`. `statusLabel` in `TeamPage` shows those as Approved and Rejected.
- Empty copy: “No join requests yet” when both lists are empty; “No pending join requests.” and “No resolved join requests yet.” when only one side is empty.

**Missing:** Nothing the statement requires. History also includes other resolved actions (`statusLabel` shows Cancelled, and any other resolved action as “Resolved”), because the split is `resolvedAt`, not only `APPROVED` / `REJECTED`. The statement does not forbid that. A page with zero requests shows one empty line instead of two empty tables.

## CR-026

**Statement:** The unlabeled day pickers on the team activity page, and the day pickers on the admin audit log, should be labeled.

**Status:** implemented

**Place named:** Team > Activity, and the admin audit log. Both screens render `AuditLogPanel` (`frontend/react/src/components/AuditLogPanel.tsx`). `TeamPage` passes `auditApi.dealershipLog`. `AdminPage` (`frontend/react/src/pages/AdminPage.tsx`) passes `auditApi.platformLog` on the audit tab.

**Present:**

- The two `type="date"` inputs are wrapped in `<label className="filter-date">` with the visible text “From date” and “To date”.
- `frontend/react/src/styles.css` (`.filters > .filter-date`) lays that caption out beside the picker (`inline-flex`). The comment in that rule calls the caption visible.
- `auditApi.logParams` (`frontend/react/src/api/audit.ts`) sends those days as `from` (start of the selected local day) and `to` (start of the day after the selected day). `AuditService.Filtered` (`backend/dotnet/DealerOps.Core/Audit/AuditService.cs`) treats `From` as inclusive and `To` as exclusive.

**Missing:** Nothing the statement requires. The source does not give the label words. The code uses “From date” and “To date” on both screens, because they share `AuditLogPanel`.

## CR-027

**Statement:** The activity log should be searchable by the change that was made.

**Status:** implemented

**Place named:** The inventory statement does not name a screen. The following item (CR-028) names Team > Activity, and `07-workflows-and-ui.md` W12 places this search on that tab. The example in the source is searching “password” to find login requests made with passwords.

**Present:**

- `AuditLogPanel` has an input with placeholder and `aria-label` “Search changes”, bound to `draft.q`. Enter or the Search button applies it. `TeamPage` loads that panel with `auditApi.dealershipLog`, which sends `q` to `GET /api/v1/dealer/audit`.
- `AuditLogFilter.Q` (`backend/dotnet/DealerOps.Core/Audit/Dto/AuditLogFilter.cs`) is documented as free text matched, ignoring case, against the action, the record type, and the stored change values (new and previous).
- `AuditService.Filtered` applies `Q` with a case-insensitive substring on `FieldSummary` and `PreviousValues`, and also on action and entity-type wire names that contain the text. `AuditController.Dealership` binds that filter on `GET /api/v1/dealer/audit`.
- Password sign-in stores the method in the change summary, not the secret. `AuthService.RecordLogin` and `LoginFailed` (`backend/dotnet/DealerOps.Core/Dealer/AuthService.cs`) write `method` = `password` (and, on failure, a `reason` such as `bad_password` or `no_password`). The class comment says the typed password is never stored. A search for “password” therefore matches those stored summaries. `RecordLogin` sets `dealerId` from the active membership, so a member’s password sign-in is on that dealership’s activity log (`ListDealership` filters `DealerId` to the tenant).

**Missing:** Nothing the statement requires. The match is the stored change JSON (plus action and record type), not a dedicated “change only” field. “password” also matches failure reasons and any other stored text that contains that substring. The typed password itself is not in the row.

## CR-028

**Statement:** On Team > Activity, the search options and the columns should appear in the same order.

**Status:** implemented

**Place named:** Logged in as any manager account > Team > Activity (`TeamPage` activity tab, `AuditLogPanel` with `showDealer` left false).

**Present:**

- The panel comment states the input order: When, Actor, Action, Record, Dealership, Changes. On Team activity the Dealership id input is omitted because `showDealer` is false.
- Filter order in that case: “From date”, “To date”, “Actor username”, Action (`select`, `aria-label` “Action”), Record type (`select`, `aria-label` “Record type”), “Search changes”, then Search and Reset.
- Column order from the same component, without the admin-only Dealership column: When (`createdAt`), Actor (`actorUsername`), Action (`action`), Record (`entityType`), Changes (`summaryText` of `fieldSummary` and `previous`), Source IP (`clientIp`).
- From date and To date are the two controls for When, and they sit first. Actor, Action, Record, and Changes then follow that column sequence. Source IP is the last column and has no search control.

**Missing:** Nothing the statement requires. The source does not say which side to reorder, or that every column needs a search box. Search and Reset are actions, not a column. The Action and Record controls have an accessible name and no separate visible caption; CR-026’s labeling request is only for the day pickers.
