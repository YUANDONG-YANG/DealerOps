# Implementation check: CR-039 through CR-041

Checked against the active .NET backend (`DealerOps.Core`, `DealerOps.Gateway`) and `frontend/react`. Java and Vue were not used. The analysis notes in this folder describe an older lead search and a final won/lost stage; the symbols below are what the current code does.

| CR | Status | What the code does |
| --- | --- | --- |
| CR-039 | implemented | Leads has a vehicle search box. `vehicle` matches year, make, and model, and also VIN. |
| CR-040 | implemented | Typing in Customer name reloads the lead list after a 300 ms pause, as DMS and CRM do. |
| CR-041 | partial | A closed lead can be reopened to an open stage, except a won lead sold to that customer, and except when another open lead already uses the same customer and vehicle. |

## CR-039

**Statement:** Leads should have a search box for vehicle name.

**Status:** implemented

**Present:** The Leads filter row has a second search box, placeholder and aria-label `Vehicle`, bound to `filters.vehicle`. Typing updates that filter; picking a suggestion or pressing Enter applies it. After 300 ms the page calls `leadsApi.list` with `vehicle`. Suggestions come from the same list call and show each matching lead's `year make model` label.

`LeadController.List` accepts query parameter `vehicle` and passes it to `LeadService.List`. That method keeps leads whose vehicle's `ModelYear + " " + Make + " " + Model` contains the term, or whose `Vin` contains the term. Soft-deleted and sold vehicles stay searchable. Leads with no vehicle do not match. The list column `Vehicle of interest` renders the same `year make model` string (`vehicleLabel` in `LeadsPage`).

The gateway forwards `/api/v1/{**catch-all}` to Core, so this query reaches `LeadController`. `dealer-platform/openapi.yaml` `listLeads` documents `vehicle` as year, make, and model, or VIN (`operationId: listLeads`).

**Missing:** Nothing required by the sentence. The document does not define "vehicle name". The box label is `Vehicle`, not `Vehicle name`. Stock number is not part of this match. VIN is included in addition to the displayed name.

**Opened:** `frontend/react/src/pages/LeadsPage.tsx` (`LeadsPage`, `vehicleLabel`, `FILTER_DEBOUNCE_MS`, `BLANK_FILTERS`); `frontend/react/src/api/leads.ts` (`leadsApi.list`, `LeadFilters`); `frontend/react/src/components/SearchSuggest.tsx` (`SearchSuggest`); `backend/dotnet/DealerOps.Core/Lead/LeadController.cs` (`List`); `backend/dotnet/DealerOps.Core/Lead/LeadService.cs` (`List`); `backend/dotnet/DealerOps.Core/Lead/Dto/LeadVehicleBrief.cs` (`LeadVehicleBrief`); `backend/dotnet/DealerOps.Gateway/appsettings.json` (route `dealer-core-public`); `dealer-platform/openapi.yaml` (`listLeads`).

## CR-040

**Statement:** Typing in the leads customer-name box should update the list as the user types, as on the DMS and CRM pages.

**Status:** implemented

**Present:** The Leads Customer name box is a `SearchSuggest` whose `onChange` sets `filters.q`. An effect on `filters.q` waits `FILTER_DEBOUNCE_MS` (300) and then calls `load(0, filters)`, which requests `GET /api/v1/leads` with `q`. The same pause applies to the vehicle box. Enter and the Search button still request the list immediately. Picking a customer-name suggestion sets `q` to that name and loads at once.

`LeadService.List` treats `q` as a substring of the customer `Name` (`Contains`), including customers that are soft-deleted. It does not match email or phone.

DMS and CRM use the same pause-then-reload pattern. `DmsPage` copies typed drafts into the list filters after `FILTER_DEBOUNCE_MS` (350). `CrmPage` copies `filters.q` into `applied` after `SEARCH_DEBOUNCE_MS` (300), and the list effect loads `applied`. Leads uses 300 ms, the same delay as CRM.

**Missing:** Nothing required by the sentence. Stage, Owner, and Overdue only on the Leads page still wait for Search or Reset; the customer-name box does not. Customer-name search does not include email or phone; the CR asks only for the name typed into that box.

**Opened:** `frontend/react/src/pages/LeadsPage.tsx` (`LeadsPage`, `load`, `FILTER_DEBOUNCE_MS`); `frontend/react/src/pages/DmsPage.tsx` (`DmsPage`, `FILTER_DEBOUNCE_MS`, `draftsPending`); `frontend/react/src/pages/CrmPage.tsx` (`CrmPage`, `SEARCH_DEBOUNCE_MS`, `applied`); `frontend/react/src/components/SearchSuggest.tsx` (`SearchSuggest`); `frontend/react/src/api/leads.ts` (`leadsApi.list`); `backend/dotnet/DealerOps.Core/Lead/LeadService.cs` (`List`); `backend/dotnet/DealerOps.Core/Lead/LeadController.cs` (`List`).

## CR-041

**Statement:** A closed lead must be reopenable, including after an accidental closure.

**Status:** partial

**Present:** Opening a won or lost lead shows `Reopen as` (New, Contacted, or Qualified; default Contacted) and `Reopen lead`. `leadsApi.reopen` posts `{ stage, version }` to `/api/v1/leads/{id}/reopen`. `LeadController.Reopen` calls `LeadService.Reopen`.

`Reopen` requires the current version, requires the lead to be won or lost, and requires the target stage to be open. It clears `LostReason`, writes an audit `UPDATE` with `stage` and `reopened: true`, and returns the updated detail. The stage dropdown, owner, follow-up, and vehicle of interest stay disabled while the lead is closed; notes can still be added. `LeadService.Patch` still rejects a closed lead with `409` `LEAD_CLOSED` (`Won and lost leads cannot be changed.`). The close confirm text says won and lost leads stay locked until someone reopens them.

The gateway catch-all proxies this POST to Core for a `Dealer.User` token. `dealer-platform/openapi.yaml` documents it as `reopenLead`.

**Missing:** Not every closed lead can be reopened.

- A won lead whose vehicle is `SOLD` and linked to that lead's customer is rejected with `409` `LEAD_CLOSED` and the message `This lead's vehicle was sold to this customer, so the won lead cannot be reopened.` (`SoldToLeadCustomer`). A lost lead is not subject to that sale check.
- Reopen is also rejected with `409` `LEAD_DUPLICATE` when another open lead already exists for the same customer and vehicle (`RequireNoOpenDuplicate`).
- The drawer still shows `Reopen lead` in the sold-won case; the refusal appears only after the click (`mapWrite`).

The CR does not name the restored stage. The page lets the user pick New, Contacted, or Qualified. No reopen reason is collected. The analysis note that reopen would be a `PATCH` is not how this is built; the working path is `POST /api/v1/leads/{id}/reopen`.
