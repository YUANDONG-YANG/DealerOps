## CR-013

**Statement:** On Team > Members, for any logged-in user, Role, Source, and Date Added must be sortable.

**Status:** implemented

**Place named:** Team → Members (`/team`, Members tab in `frontend/react/src/pages/TeamPage.tsx`). The inventory source says “Date Added (when added).” `05-data-model.md` treats that as `membership.created_at`. C-03 asks whether “any user account” means staff as well; the same note says the document does not give staff the Team page.

**Present:**

- `frontend/react/src/router.tsx` mounts `/team` behind `ManagerGuard`. That guard redirects anyone whose `dealerRole` is not `MANAGER`. `AppLayout` adds the Team menu item only when `isManager` is true.
- `TeamPage` loads members with `membersApi.list()` (`frontend/react/src/api/members.ts`), `GET /api/v1/members`. The list is not paged.
- `MemberDirectoryController.List` (`backend/dotnet/DealerOps.Core/Dealer/MemberDirectoryController.cs`) returns `MemberDirectoryService.ActiveMembers()`. That method returns every active membership of the caller’s dealership. `MemberOption.JoinedAt` is `Membership.CreatedAt` stored as UTC (`backend/dotnet/DealerOps.Core/Dealer/Dto/MemberOption.cs`). `Source` comes from `AccountSource.For`. `DealerRole` is the membership role.
- The Members table headers are Member, Username, then `SortableTh` for Role (`sortKey` `dealerRole`), Source (`source`), and Joined (`joinedAt`), then Actions. `useSort(members, memberSortValue)` in `frontend/react/src/components/TableSort.tsx` sorts the full array in the browser. Until a header is clicked, `sortRows` leaves the server order (username).
- `memberSortValue` compares Role by `enumLabel(dealerRole)`, Source by `accountSourceLabel(source)`, and the date column by `joinedAt`. The cell renders `dateTimeLocal(m.joinedAt)`.

**Missing:** Nothing required to sort those three fields. The date header text is “Joined”, not “Date Added”. Staff and platform admins never reach this table because of `ManagerGuard`.

## CR-014

**Statement:** On Team > Activity, for any logged-in user, the listed columns must be sortable.

**Status:** partial

**Place named:** Team → Activity. Inventory columns: When, Actor, Action, Record (type followed by number), Source IP, Location. `08-api-and-integrations.md` §8.3 and `05-data-model.md` §8 say Location is not defined (place name, dealership, or something else) and is not inferred as geocoding. C-03 is the same actor question as CR-013.

**Present:**

- The Activity tab renders `AuditLogPanel` with `load={auditApi.dealershipLog}` and `showDealer` left false (`TeamPage`). The same panel is used by the admin audit log.
- `auditApi.dealershipLog` (`frontend/react/src/api/audit.ts`) calls `GET /api/v1/dealer/audit` and sends `sort` as `field,asc|desc` via `sortParam`. Page size in `logParams` is 10. A header click in `AuditLogPanel` stores `SortState`, resets to page 0, and reloads.
- Sortable headers in `AuditLogPanel`: When (`createdAt`), Actor (`actorUsername`), Action (`action`), Record (`entityType`, rendered as `` `${entityType} #${entityId}` ``), and Source IP (`clientIp`). Changes is not sortable. Dealership is omitted on this tab.
- `AuditController.Dealership` (`backend/dotnet/DealerOps.Core/Audit/AuditController.cs`) binds `AuditLogFilter.Sort` and calls `AuditService.ListDealership`. `AuditService.Sorted` allows `createdAt`, `actorUsername`, `action`, `entityType`, `dealerId`, and `clientIp` (`SortFields`). Unknown `sort` values fail validation in `Paging.ParseSort`. The order is applied before `Skip`/`Take` in `PageOfLog`, so the sort covers the filtered log, not only the current page. With no `sort`, the order is `CreatedAt` descending, then `Id` descending.
- Record sort is `EntityType` in the requested direction, then `EntityId` ascending (`ThenBy`, not reversed when the header is descending), then `CreatedAt` and `Id` descending.
- `DealerOps.Gateway` proxies `/api/v1/{**catch-all}` to Core (`dealer-core-public` in `backend/dotnet/DealerOps.Gateway/appsettings.json`). That route has no query transform. `Program.cs` calls `MapReverseProxy`.
- `AuditEventEntity` stores `client_ip` as `ClientIp`. `AuditItem` returns `ClientIp` on this log.

**Missing:** A Location column, a location value on `AuditItem` / `AuditEventEntity`, and a location entry in `SortFields`. The analysis does not define what Location would contain. The Team page remains manager-only (`ManagerGuard`; `ListDealership` calls `TenantGuard.RequireManager`).

## CR-015

**Statement:** On Team > Join Requests, for any logged-in user, Requested, Status, and Resolved must be sortable.

**Status:** implemented

**Place named:** Team → Join requests (`TeamPage` tab `requests`). A-17 asks whether Status and Resolved belong on the current (pending) table. W10 splits the screen into requests still waiting and past requests.

**Present:**

- `TeamPage.load` calls `notificationsApi.list(true)` (`frontend/react/src/api/notifications.ts`), `GET /api/v1/dealer/notifications?includeResolved=true`, then keeps rows whose `kind` is `JOIN_REQUEST`.
- `NotificationController.List` (`backend/dotnet/DealerOps.Core/Notifications/NotificationController.cs`) returns `NotificationService.List`. For a manager and `includeResolved=true`, that query is every notification of the caller’s dealership, newest first, with no page cut. Each row includes `createdAt`, `resolvedAt`, `resolvedBy`, and `resolvedAction`.
- The tab renders two tables. Pending is `resolvedAt == null`. History is the rest.
- Pending headers include `SortableTh` Requested (`createdAt`). `useSort` sorts every pending row. Status and Resolved are not columns on this table; every pending row is unresolved.
- History headers include `SortableTh` for Requested (`createdAt`), Status (`status`), and Resolved (`resolvedAt`). `requestSortValue` compares Status by `statusLabel` text (Approved, Rejected, Cancelled, or Resolved) and Resolved by `resolvedAt`. `historySort.sorted` is sliced into pages of 10 after the sort, so the sort is the full history, not one page.
- Until a header click, both tables keep the API order (newest `createdAt` first).

**Missing:** Nothing the statement requires of the three columns. Status and Resolved are sortable only on History, which is the table that shows them. Pending has no Status or Resolved header. The tab is manager-only, same gate as CR-013. History also includes `CANCELLED` rows because any non-null `resolvedAt` is history; the statement does not exclude them.

## CR-016

**Statement:** On the platform-admin audit log, the listed columns must be sortable.

**Status:** partial

**Place named:** Platform admin → Audit log. Inventory columns: When, Actor, Action, Record (type followed by number), Location. Source IP is not in this list. `08-api-and-integrations.md` §9 says extra sortable columns are allowed. Location is the same undefined column as CR-014.

**Present:**

- `AdminPage` (`frontend/react/src/pages/AdminPage.tsx`) shows an “Audit log” tab. `/admin` is behind `AdminGuard` in `router.tsx` (`role === 'Platform.Admin'`).
- That tab renders `AuditLogPanel` with `load={auditApi.platformLog}` and `showDealer`. `auditApi.platformLog` calls `GET /api/v1/admin/audit` with the same `sort` parameter as the dealership log.
- Sortable headers: When, Actor, Action, Record, Dealership (`dealerId`, because `showDealer` is true), and Source IP. Changes is not sortable. Record text is the same `entityType #entityId` form.
- `AuditController.Platform` binds `AuditLogFilter` and calls `AuditService.ListPlatform`, which requires `TenantGuard.RequireAdmin` and uses the same `Sorted` / `PageOfLog` path as the dealership log, including the optional `dealerId` filter. `dealerId` is one of `SortFields`.
- Gateway forwarding is the same `/api/v1/**` proxy as CR-014.

**Missing:** A Location column and any location field to sort. Source IP is sortable even though this CR does not name it. Record’s secondary `EntityId` order stays ascending when the header is descending, same as CR-014.
