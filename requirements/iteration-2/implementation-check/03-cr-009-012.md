# Implementation check: CR-009 through CR-012

Checked the active .NET 10 services (`DealerOps.Core`, `DealerOps.Gateway`, `DealerOps.AiService`) and `frontend/react`. Java and Vue were not used. `DealerOps.AiService` has no registration, role, or list-sort behavior for these items.

Clarifying notes used from this analysis folder: `07-workflows-and-ui.md` (W5, W6, W7), `06-auth-roles-tenancy.md` §2, `08-api-and-integrations.md` §6.5, §7.1, and §9, and `10-design-and-code-impact.md` §5 and §6. Those notes say the dealership inquiry and the dealership-admin role are postponed, and that a paged list should sort on the server.

## CR-009

- **Status:** partial
- **Statement:** Home-page account creation should become a way for dealerships to inquire about using the service, and for now the create-account button should be removed.
- **Present:** `LandingPage` no longer shows a Create account control in the header, hero, or bottom call to action. The header `landing-auth-links` block has only Sign in (`Link` to `/login`). The hero `landing-actions` block has Sign in and Decode a VIN. The bottom section says dealership staff sign in with an account the dealership or platform administrator set up, and its only button is Sign in. The page footer links Disclaimer and Shop vehicles.
- **Missing:** Nothing on the home page collects a dealership's inquiry about using the service. The buyer-site form in `ShopPage` (`buyerSiteApi.inquire`) asks about a listed vehicle; it is not that inquiry. `RegisterPage` is still mounted at `/register` in `AppRoutes`, and `LoginPage` still links Create account to `/register`. The gateway still allows anonymous `POST /api/v1/auth/register`. One home-page control still opens registration: the sample-ad link "Check your own ads →" in `LandingPage` (`Link` to `/register`). The change note says a different account-creation method still needs a client discussion, and that removing the home-page button is enough for now. The inquiry form, its fields, and a new endpoint are not specified in that note.
- **Opened:** `frontend/react/src/pages/LandingPage.tsx` (`LandingPage`); `frontend/react/src/pages/RegisterPage.tsx`; `frontend/react/src/pages/LoginPage.tsx`; `frontend/react/src/router.tsx` (`AppRoutes`); `frontend/react/src/pages/ShopPage.tsx`; `frontend/react/src/api/buyerSite.ts` (`inquire`); `backend/dotnet/DealerOps.Gateway/Program.cs` (anonymous auth paths).

## CR-010

- **Status:** not-applicable
- **Statement:** A dealership-specific admin, owner, or regional-manager account, with some admin capabilities limited to one dealership, is optional and should be discussed before it is fully implemented.
- **Present:** Account roles are `AppRole.PlatformAdmin` (`Platform.Admin`) and `AppRole.DealerUser` (`Dealer.User`). Membership roles are `DealerRole.Manager` and `DealerRole.Staff`. The gateway role gate accepts only `Platform.Admin` and `Dealer.User`. A platform-admin token is blocked from business routes. Inside a dealership, `TenantGuard.RequireManager` is the extra check; business lists use `TenantGuard.RequireTenantId` for any bound dealer user. There is no dealership-admin, owner, or regional-manager value.
- **Missing:** No code behavior is required yet. The change note says the account is optional and should be discussed before full implementation, and it does not list the powers. The privilege order printed after the statement includes that account between platform admin and dealership manager. That rung is not in the code. The roles that do exist stay in the order platform admin, then manager, then staff, then a signed-out visitor. That matches the note's instruction not to add the role in this pass.
- **Opened:** `backend/dotnet/DealerOps.Core/Dealer/AppRole.cs` (`AppRole`); `backend/dotnet/DealerOps.Core/Dealer/DealerRole.cs` (`DealerRole`); `backend/dotnet/DealerOps.Core/Common/Tenant/TenantGuard.cs` (`RequireDealerUser`, `RequireManager`, `RequireTenantId`, `RequireAdmin`); `backend/dotnet/DealerOps.Gateway/Program.cs` (role gate).

## CR-011

- **Status:** implemented
- **Statement:** On DMS, for any logged-in user, the listed columns must be sortable.
- **Present:** `DmsPage` marks these columns sortable: Stock # (`stockNumber`), Body (`bodyType`), Source (`source`), Condition (`conditionCode`), Cost (`purchaseCost`), List price (`listPrice`), Date added (`addedOn`), Open WOs (`openWorkOrders`), and Status (`status`). A header click calls `onSort`, which reloads `vehiclesApi.list` with `sortParam` (`field,asc|desc`). `VehicleController.List` accepts `sort`, and `VehicleService.Sorted` orders the full filtered query by those fields before `Skip`/`Take`. The same page also sorts Leads, Sold by, Sold to, and Date sold. The change note allows extra sortable columns. Year Make Model and VIN are shown and are not sortable; they are not in the named list. `/dms` is under `DealerGuard`, so both manager and staff dealer users reach it. `VehicleService.List` calls `TenantGuard.RequireTenantId`, which does not require a manager. A platform admin does not open `/dms` and is blocked from `/api/v1/vehicles`; the note scopes this screen to any dealership user.
- **Missing:** Nothing from the named DMS list.
- **Opened:** `frontend/react/src/pages/DmsPage.tsx` (`DmsPage`, `columns`, `load`); `frontend/react/src/components/DataTable.tsx` (`DataTable`); `frontend/react/src/components/TableSort.tsx` (`sortParam`, `SortableTh`); `frontend/react/src/api/vehicles.ts` (`vehiclesApi.list`); `frontend/react/src/router.tsx` (`DealerGuard`); `backend/dotnet/DealerOps.Core/Vehicle/VehicleController.cs` (`List`); `backend/dotnet/DealerOps.Core/Vehicle/VehicleService.cs` (`SortFields`, `Sorted`, `List`).

## CR-012

- **Status:** partial
- **Statement:** On Leads, for any logged-in user, every column must be sortable.
- **Present:** `LeadsPage` passes five data columns to `DataTable`, and each has `sortable: true`: Customer (`customerName`), Vehicle of interest (`vehicle`), Stage (`stage`), Owner (`ownerUsername`), and Next follow-up (`nextFollowUpOn`). Those are the fields on `LeadListItem` that the table shows (`overdue` is rendered inside Next follow-up, not as its own column). The Actions header is the row action Open, not a data column, and it does not sort. `/leads` is under the same `DealerGuard` as DMS. `LeadController` is `[Authorize]`, and `LeadService.List` uses `TenantGuard.RequireTenantId`, so manager and staff can load the list. A platform admin does not open this page.
- **Missing:** The header click does not reload the list. `LeadsPage` `load` calls `leadsApi.list` with page and size 10 and no sort argument. `leadsApi.list` has no sort parameter. `LeadController.List` has no `sort` query. `LeadService.List` always uses `OrderByDescending(CreatedAt)` then `Id` before paging. `DataTable` therefore sorts only the rows already loaded for the current page (`useSort` when `onSort` is omitted). Later pages stay in created-at order. The analysis note infers a server sort for this paged list; the change text itself only says every column is sortable and does not name a query parameter.
- **Opened:** `frontend/react/src/pages/LeadsPage.tsx` (`LeadsPage`, `load`); `frontend/react/src/components/DataTable.tsx` (`DataTable`); `frontend/react/src/api/leads.ts` (`leadsApi.list`); `backend/dotnet/DealerOps.Core/Lead/LeadController.cs` (`List`); `backend/dotnet/DealerOps.Core/Lead/LeadService.cs` (`List`); `backend/dotnet/DealerOps.Core/Lead/Dto/LeadListItem.cs` (`LeadListItem`).
