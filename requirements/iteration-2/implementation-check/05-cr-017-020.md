# Implementation check: CR-017 through CR-020

Checked against the active .NET backend (`DealerOps.Core`) and `frontend/react`. Java and Vue were not used. Wording is from `requirements/update-cr/analysis/01-change-inventory.md`. Screen mapping is from `requirements/update-cr/analysis/07-workflows-and-ui.md` (W7) and `requirements/update-cr/analysis/03-modified-behavior.md` (sortable-columns table). `requirements/update-cr/analysis/08-api-and-integrations.md` §9 notes that these lists were specified without a sort query; that note is an inference, not an extra requirement. Sort direction, multi-column sort, and a default sort are not stated (`03-modified-behavior.md`).

Shared sort behavior that the screens below call: `nextSort`, `useSort`, and `SortableTh` in `frontend/react/src/components/TableSort.tsx`. A new column starts ascending; the same column flips direction. `useSort` reorders the array it is given and leaves the original order until a header is clicked.

## CR-017

**Statement:** On platform-admin Ad Rules, Enabled and Severity must be sortable.

**Status:** implemented

**Present:** Admin tab `Ad rules` in `AdminPage` renders `ComplianceRulesPanel`. That panel loads `complianceRulesApi.list()` (`GET /api/v1/admin/compliance-rules`) into `rules`, then `useSort(rules)`. The headers are `SortableTh` with `sortKey` `enabled` and `severity`, and the body maps `ruleSort.sorted`.

`ComplianceRuleController.List` returns `ComplianceRuleService.List()`, which returns every known rule (`IReadOnlyList<RuleOverrideResponse>`), not a page. `RuleOverrideResponse` carries `Enabled` and `Severity`. Core JSON uses camel case, so those are `enabled` and `severity`, matching the sort keys and the `ComplianceRule` type. `enabled` is a boolean; `TableSort.compareValues` compares booleans as numbers. `severity` is the string `BLOCK` or `REVIEW`.

**Missing:** Nothing for the two named columns. The list is not paged, so the client sort covers the catalog the API returns. Rule, Message, and Action are not sortable; the request does not name them.

## CR-018

**Statement:** On platform-admin Pending accounts, Registered must be sortable.

**Status:** partial

**Present:** Admin tab `Pending accounts` renders `PendingAccounts` with no `dealerId`. That table has `SortableTh` label `Registered`, `sortKey` `createdAt`, and the body maps `pendingSort.sorted` from `useSort(pending)`. `PendingUser.createdAt` matches `PendingUserResponse.CreatedAt`. An ISO timestamp sorts as text in `TableSort`.

**Missing:** The table does not sort every pending account. `PendingAccounts` calls `adminApi.pendingUsers()` with no page. `adminApi.pendingUsers` always sends `size: 10` to `GET /api/v1/admin/pending-users` and the component keeps only `r.data.items`. It does not read `totalElements` and has no page control. `AdminPendingUserController.List` and `MembershipService.Pending` take `page` and `size`, order by `CreatedAt` descending, and accept no `sort` parameter. Header clicks reorder at most those ten rows. Accounts past that page are not in the sort.

The same component, when `dealerId` is set (Dealerships → Staff → Pending accounts), does not render a Registered header. It prints `Registered {dateTimeLocal(u.createdAt)}` inside the Account cell and maps `pending`, not `pendingSort.sorted`. That path is not the named Pending accounts tab. It uses the same first-page fetch.

## CR-019

**Statement:** On platform-admin Members, Dealership, Role, Sign-in, and Status must be sortable.

**Status:** implemented

**Present:** Admin tab `Members` in `AdminPage`. `loadFlatMembers` walks every dealership (`fetchAllDealers`) and every member page (`fetchDealerMembers`, which loops `adminApi.members` until `items.length` reaches `totalElements`). Each row is a `FlatMember`: `Member` plus `dealerId` and `legalName`. `MemberResponse` supplies `active`, `signInMethod`, and `dealerRole`.

`memberSort = useSort(flatMembers)` sorts that full array. `pagedMembers` is `memberSort.sorted.slice(memberPage * 10, memberPage * 10 + 10)`. The `DataTable` receives those rows with `sort={memberSort.sort}` and `onSort`, so `DataTable` shows the parent order instead of sorting the page again. A header click calls `memberSort.toggle` and resets `memberPage` to 0. The four columns are:

| Header | `key` passed to `useSort` | Value compared |
| --- | --- | --- |
| Dealership | `legalName` | Dealership legal name on the row |
| Role | `dealerRole` | `MANAGER` or `STAFF` (`enumLabel` is display only) |
| Sign-in | `signInMethod` | `password`, `google`, or `firebase` (`SignInTag` is display only) |
| Status | `active` | Boolean; the cell text is Active or Inactive |

A member search passes `filterQ` into `fetchDealerMembers` before the sort, so the sort covers the filtered set that was loaded.

**Missing:** Nothing for the four named columns on this tab. Username, Contact, Password, Change role, and Account are not sortable; the request does not name them. The staff drawer inside a dealership (`drawerMembers`) is a different table: its Role, Sign-in, and Status headers are plain `th` elements and that table is not sorted. The request names platform-admin Members, which is the Members tab.

## CR-020

**Statement:** In any manager audit menu, Action, Actor, and When must be sortable.

**Status:** partial

The inventory line is "When logged in as manager account > Any menu with audit" and the columns are Action, Actor, and When. W7 maps that to the record audit trail (`AuditTrail`) on the DMS vehicle drawer, the CRM customer drawer, the lead drawer, and the ad workspace. Team → Activity is a different request (CR-014) and is not scored here.

**Present:** `AuditTrail` renders `SortableTh` for Action (`sortKey` `action`), Actor (`actorUsername`), and When (`createdAt`). `trailSortValue` compares Action with `actionText(row)`, Actor with `actorUsername`, and When with `createdAt`. `useSort(rows, trailSortValue)` reorders the `rows` prop. The trail is mounted only when `dealerRole === 'MANAGER'`:

| Menu | Caller | Fetch |
| --- | --- | --- |
| DMS vehicle drawer | `DmsPage` `loadAudit` | `auditApi.list({ entityType: 'VEHICLE', entityId, page, size: 10 })`, with `page`, `total`, and `onPage` |
| CRM customer drawer | `CrmPage` `loadAudit` | `auditApi.list({ entityType: 'CUSTOMER', entityId, page, size: 10 })`, with pager props |
| Lead drawer | `LeadsPage` `loadAudit` | `auditApi.list({ entityType: 'LEAD', entityId })` (defaults: page 0, size 10); `AuditTrail` gets `rows` only |
| Ad workspace | `AdsPage` `loadAudit` | `auditApi.list({ entityType: 'LISTING', entityId, page, size: 10 })`, with pager props |

`auditApi.list` calls `GET /api/v1/audit` and does not send `sort`. `AuditService.List` documents the history as newest first and requires a manager (`TenantGuard.RequireManager`). `List` for a lead or listing, `CustomerHistory`, and `VehicleHistory` all order by `CreatedAt` descending and then page. None of those methods take a sort field. `AuditService.Sorted` (`createdAt`, `actorUsername`, `action`, and others) is used by the admin and dealership logs, not by `List`.

**Missing:** A header click reorders only the rows already loaded. `AuditTrail` states that in a comment: "Sorts the loaded page". On DMS, CRM, and Ads, the next page is another newest-first request of 10; the header sort is not sent with that request. On Leads, `totalElements` is ignored and there is no pager, so events after the first 10 are not on screen and cannot be sorted into view. Summary is not a sortable column; the request does not name it.
