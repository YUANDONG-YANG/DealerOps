1. Chosen Strategy and Justification

Blue/Green deployment, with a canary ramp on the green environment before the full cut-over.

These are two layers of one strategy, not two competing strategies. Blue/Green is the environment and rollback model: two complete production environments, only one of them live, and a routing change as the release action. Canary is the traffic-exposure control layered on top of it: it decides how fast customers are moved from blue to green. Blue/Green provides the escape route; the canary ramp limits how many customers need it.

The decisive constraint in the scenario is that the rollout must not affect the ongoing operations of the live system. An e-commerce site takes revenue continuously; a checkout outage costs money and customer trust immediately, and a bad release that is only discovered after everyone is on it is worse than a slow release. Blue/Green answers both:

  • No downtime. The current version (blue) keeps serving every request while the new version (green) is built, deployed and verified alongside it. The switch is a change of traffic routing, not a restart of the application.
  • Rollback is instant and cheap. If anything is wrong after the cut-over, traffic is pointed back at blue, which is still running and still warm. Recovery is seconds, not a redeploy.
  • Production verification before exposure. Green runs on real production infrastructure with real configuration, so smoke tests exercise the environment that will actually serve customers — something a staging environment can only approximate.

The canary ramp is added on top because Blue/Green on its own is still a single moment where 100 % of customers move at once. Sending 5 %, then 25 %, then 50 % of traffic to green first means a defect that only shows up under real user behaviour — a payment edge case, a slow query under load — is caught while it affects a small fraction of shoppers, and the blast radius stays small.

Why not the alternatives

StrategyWhy it was not chosen
Basic (big-bang)Requires stopping the running version. Guaranteed downtime, all users exposed at once, and rollback means redeploying the old build under pressure. Directly violates the "without affecting ongoing operations" requirement.
RollingNo downtime, but both versions serve live traffic for the whole rollout with no clean boundary, and rollback means rolling back instance by instance. Mixed-version behaviour is awkward for a session-based checkout flow.
A/B testingA product-experiment technique for comparing variants against a business metric, not a release-safety technique. Useful later for the new features, not for shipping the release itself.
ShadowExcellent for validating performance with mirrored traffic, but it never serves real users, so it cannot complete the release. It is worth using for the riskiest services as a pre-step, not as the strategy.

2. Deployment Plan

Phase 0 — Preparation (before release day)

  • Freeze the release branch; tag the release in Git (semantic version, e.g. v2.4.0).
  • Agree the go/no-go criteria in advance and in numbers: error rate below baseline + 0.5 %, p95 checkout latency within 10 % of baseline, payment success rate unchanged, no new severity-1 defects.
  • Confirm the database migration is backward compatible (expand/contract: add columns and tables now, remove nothing until the old version is retired), so blue and green can share one database safely.
  • Verify a restorable database backup and rehearse the rollback on staging.
  • Pick a low-traffic window and notify support and operations — not because downtime is expected, but so the people answering customers know a release is live.

Phase 1 — Development to artifact

StepAction
1Feature work merges to main only through a pull request with review and a green pipeline.
2CI on every commit: lint, unit tests, integration tests, dependency and container vulnerability scan.
3Build one immutable Docker image, tagged with the Git commit SHA. The same artifact is promoted through every environment; nothing is rebuilt per environment.
4Push the image to the registry; configuration comes from environment variables and a secret store, never baked into the image.

Phase 2 — Test and staging verification

StepAction
5Deploy the artifact automatically to a test environment provisioned from the same infrastructure code as production.
6Run the automated regression suite (API + end-to-end UI), plus performance tests against the checkout path.
7Run the database migration against a production-sized copy and measure how long it takes.
8UAT sign-off on staging for the new functionality and confirmation of the bug fixes in this release.

Phase 3 — Production rollout (Blue/Green + canary)

StepAction
9Apply the backward-compatible database migration while blue is still serving all traffic. Blue ignores the new columns; green will use them.
10Provision the green environment from infrastructure code and deploy the tagged image to it. Green receives no customer traffic yet.
11Smoke-test green directly on an internal hostname: health checks, login, product search, add to cart, a full checkout against the payment provider's sandbox credentials, and the specific bug fixes in this release. A live-money test order is deliberately not part of the smoke test: it would create a real charge, a real order record and real customer data that then have to be isolated, reconciled and reversed. If a live-path check is ever judged necessary, it needs a flagged internal test account, prior finance authorisation and a documented reconciliation step.
12Warm green: pre-load caches and connection pools so the first real customers do not pay the cold-start cost.
13Canary: route 5 % of traffic to green via weighted load-balancer targets. Hold 15–30 minutes and watch the go/no-go metrics.
14Ramp 25 % → 50 % → 100 %, pausing at each step and re-checking the same metrics. Any breach stops the ramp.
15Cut over fully: green is now production. Keep blue running and untouched for 24 hours.

Phase 4 — Post-deployment

StepAction
16Monitor dashboards and alerts for the first hour with the release team on hand; track orders per minute, payment success, error rate, latency and infrastructure saturation.
17Run post-deployment verification: a scripted real-order check, and a reconciliation of order and payment records.
18After the 24-hour soak, decommission blue and release its resources. Run the contract phase of the migration (drop now-unused columns) in a later release.
19Release notes published; retrospective held; any manual step encountered during the rollout is turned into a pipeline task.

Rollback procedure

Trigger: any go/no-go criterion breached, or a severity-1 defect reported from production.

  1. Shift the load-balancer weight back to 100 % blue — the only action needed, and it takes seconds because blue never stopped running.
  2. Disable the new features behind their feature flags if the problem is feature-specific rather than release-wide.
  3. Leave the database alone. Because the migration was additive, blue runs correctly against the migrated schema; no data restore is needed, which is what makes this rollback safe.
  4. Capture logs, traces and metrics from green before tearing it down, then diagnose off the critical path.

4. Potential Challenges and How the Plan Addresses Them

ChallengeMitigation in this plan
Downtime riskBlue serves every request until green is verified; the cut-over is a routing change. Health checks gate the switch, and rollback is a weight change back to blue.
Inefficient resource utilisation (Blue/Green doubles capacity)Keep the overlap short — green is created at step 10 and blue is retired 24 hours after cut-over. Provision green with Terraform on autoscaling (and spot/preemptible capacity where the workload tolerates it) so the duplicate cost is hourly rather than permanent. Green is nevertheless provisioned and load-tested for the full expected peak before the ramp starts — under-sizing it for the canary slice alone would make green fail on capacity and produce a false release failure. Autoscaling then handles the headroom, and the duplicate cost is short-lived rather than permanent.
Database schema changes shared by both versionsExpand/contract migrations: additive only during the release, destructive changes deferred to a later release once blue is gone. This is what keeps rollback free of a data restore.
Defects that only appear under real trafficThe canary ramp exposes 5 % of users first, with hold periods and explicit numeric go/no-go criteria at every step.
In-flight customer sessions and cartsSessions and carts are stored externally (Redis/database), not in application memory, so a customer moved from blue to green keeps their cart. Connection draining lets blue finish in-flight requests.
Cold caches and slow first requestsGreen is warmed at step 12 before any customer traffic reaches it.
Configuration drift between environmentsEvery environment is built from the same Terraform modules and the same image; differences are limited to declared variables.
Human error during the rolloutNo ad hoc manual execution steps; a human approval gates the automated rollout. The pipeline performs the deployment, the ramp and the rollback; the release manager decides, the automation executes.
Third-party dependencies (payment, shipping)Smoke tests exercise the full payment path against the provider's sandbox credentials (no live-money orders), and the release is scheduled outside the provider's own maintenance windows.

5. The Role of DevOps and CI/CD

CI/CD is what makes this plan executable rather than aspirational. Continuous integration means defects are caught at commit time by tests and scans, so the artifact reaching release day has already been validated many times. Continuous delivery means the exact artifact that passed those checks is the one promoted to production — one build, many environments, no "it worked in staging" mystery caused by rebuilding. The pipeline also owns the rollout itself: provisioning green, running smoke tests, moving traffic weights, and rolling back. The riskiest and most error-prone parts of a release are therefore scripted, reviewed and repeatable instead of typed into a terminal at the end of a long day.

DevOps supplies the surrounding practice. Development and operations share one pipeline, one set of dashboards and one definition of done, so "ready to deploy" is a measured state rather than a handover. The same people who write the feature watch its metrics during the canary ramp, which shortens feedback from days to minutes. The plan's alignment with core DevOps principles:

PrincipleWhere it appears
AutomationCI pipeline, Terraform-provisioned green environment, automated smoke tests, scripted traffic ramp and rollback, Flyway migrations.
Collaboration and shared ownershipPull-request review across dev and ops, agreed go/no-go criteria set before release day, joint monitoring during the ramp, blameless retrospective afterwards.
Continuous feedback and measurementMetrics and alerts gate every ramp step; monitoring is a release control, not just an after-the-fact dashboard.
Continuous improvementEvery manual step found during a rollout becomes a pipeline task; every incident adds a test or an alert. Deployment gets cheaper and safer with each release.
Small, frequent, reversible changesFeature flags separate deploy from release, and instant rollback keeps the cost of being wrong low — which is what lets the team ship more often rather than less.

6. Reflection

6.1 What was the most challenging part of creating this plan, and why?

The database. Blue/Green is easy to describe for stateless web servers and hard to make true for the data behind them, because blue and green share one database and a schema change cannot be in two states at once. A naive migration would make rollback worthless: traffic could be pointed back at blue in seconds, but blue would then be running against a schema it does not understand. Resolving it meant designing the migration as expand/contract — additive changes during this release, destructive changes deferred to the next one — which spreads a single logical change across two releases and requires the application to tolerate both shapes in between. That is more discipline than it first appears to need.

The second difficulty was making the go/no-go criteria objective. "Looks fine" is not a criterion; under pressure, with revenue flowing, someone will always argue for continuing. Committing to numbers before release day — and agreeing that breaching them means rolling back, not debating — is as much an organisational decision as a technical one.

6.2 How would the process differ with a Basic deployment?

In short, Basic deployment trades availability and recoverability for simplicity and cost. For an internal admin tool that is a reasonable trade. For a live e-commerce site, the downtime is lost revenue and the slow rollback turns a small defect into a long incident, so the extra infrastructure cost of Blue/Green is cheap insurance.

6.3 How do infrastructure as code and microservices fit in?

Infrastructure as code is what makes Blue/Green practical rather than theoretical. Green has to be a faithful copy of blue; if it is built by hand it will not be, and the smoke tests will be validating an environment that differs from the one customers use. With Terraform, green is produced from the same reviewed modules as blue, in minutes, as often as needed. It also makes the environment disposable — it can be destroyed after the release and recreated identically for the next one, which is what keeps the duplicate-resource cost temporary. And because the infrastructure lives in Git alongside the application, an infrastructure change goes through the same review, the same history and the same rollback path as a code change. Configuration drift, the usual reason a release behaves differently in production, largely stops being possible.

Microservices change the granularity of the whole plan. If the new functionality touches only the catalogue service, only that service is deployed; the checkout and payment services are not redeployed and not put at risk. Releases become smaller, more frequent and faster to verify, and the blast radius of a bad release shrinks to one service. A canary can target the single service that changed instead of the whole site. The costs are real, though: services must stay backward compatible with each other, which means versioned APIs and contract tests in CI, and debugging a failed canary across service boundaries needs distributed tracing. Microservices also multiply the number of pipelines and environments to manage — which is precisely why they depend on the automation and infrastructure as code described above. Taken together, the three reinforce each other: IaC makes environments reproducible, microservices make changes small, and CI/CD makes shipping them routine.
