Five testing tasks on a live capstone

All five optional tasks from ai-test.md, applied to the DealerOps dealership platform. Four of the five were executed against the running system; this report explains what each task does, how it was verified, and the six defects and unstated behaviours the execution exposed.

Context

What the system under test is

DealerOps is a multi-tenant dealership platform: a React front end, a .NET 10 API split into three services, and MySQL. Multi-tenancy is the property most of these tests probe — one dealership's staff must never see another's vehicles, customers or leads — and it is enforced per request from a membership table rather than from the sign-in token.

The five tasks attach to that system at four different depths. One reads source code and never runs it. Two drive the public HTTP API. One reaches inside the service-to-service boundary to observe what leaves the trusted side. One compiles against a DTO to read the validation rules the product declares.

Verdict

A state transition table is only worth writing when a feature has real states and guarded transitions; a decision table is only worth writing when an outcome depends on a combination of conditions. The lead pipeline and the in-dealership role change were picked because each is the strongest example of one shape.

Both tables were built by reading LeadService.cs and MembershipService.cs, not only the requirement text, so each cell traces to a specific guard and each error code comes from the one mapping that produces it. Where code and requirement disagree, the table records the code.

What the tables exposed

  • Closing a lead relaxes a constraint. The one-open-lead-per-customer-and-vehicle rule applies only while the lead stays open, so the same request succeeds or fails depending only on the target stage.
  • Two guards overlap, and the overlap is the point. The sold-to-this-customer check can only fire when the vehicle is already sold, which also fails the in-stock check. It never decides whether a reopen succeeds — only which error comes back. A suite that tests the in-stock case and the sold-to-this-customer case, but not sold-to-someone-else, would still pass if the guard were deleted.
  • Condition order outranks specificity. In the role-change table, asking to make someone an owner is refused before the target is even loaded, so requesting OWNER for a username that does not exist returns 403 rather than 404. Good behaviour — it declines to confirm whether a username exists — but accidental rather than specified.
  • One rule is wider than its requirement. AUTH-27 describes a manager as able to promote a sales member; the implementation also lets a manager set a sales member back to sales. Harmless and idempotent, so it is recorded as a documentation gap, not raised as a defect.

The nine decision rules cover all 72 input combinations because evaluation short-circuits: the first four rules absorb 66 of them.

The model was given the registration and login rules — username shape, the contact requirement, the phone normalisation, the three conflict codes and the identifier resolution order — and asked for black-box cases. Its output was then checked for correctness, coverage and duplication against the requirement IDs and the two existing browser specs, and an improved, deduplicated set was written with the gaps named.

That review was done by reading. It caught several real gaps. It also passed over an expected result that is wrong, and the improved set copied the error forward — which is the most useful thing this task produced.

Finding

Username sign-in ignores case, and both reviewers said it would not

The generated case expected Pat against an account named pat to return 401, reasoning that "username match is exact". Executed: registering CaseProbeX then caseprobex returns 409 USERNAME_TAKEN, and signing in as caseprobex or CASEPROBEX both return 200 for the same account.

So the case is not merely wrong on its status code — it is not a separate equivalence class at all.

Four fields with documented limits: the registration username (3–64 characters, a restricted character set, at least one letter), a work-order task (1–200), a completion note (1–500), a cost of at least zero, and the lead list's page size. For each closed range the model listed the six off-by-one points and held every other input valid, so each row has a single cause.

Every row was then run against the live API. All forty numbered cases behaved as predicted. The two mistakes were in prose the model wrote beside the tables, which is exactly where a review stops looking.

Finding

A whitespace-only value is rejected, and for two different reasons

The model argued that any string of length 1–200 is a valid task, "including a string of spaces", since the requirement never says non-blank. The review agreed. Both were wrong: a one-space task returns 400 with fieldErrors.task set to "The Task field is required", because [Required] tests IsNullOrWhiteSpace and a single space never reaches the length check.

A one-space completion note is also rejected — but by the service, not by model validation, because a note is only required when the status becomes DONE. The service trims it to null first. That 400 carries no fieldErrors object at all, so an assertion written on fieldErrors.completionNote fails on a correct rejection.

Four questions the model had declined to answer — correctly, since its sources did not cover them — now have answers: a non-numeric or fractional page size is the group's only rejection; a cost with a third decimal is accepted and echoed, even though the column stores two; a cost sent as the JSON string "0" is coerced rather than refused; and a non-ASCII letter does not count as a letter in a username.

Verdict
Expectation wrong

The chatbot under test is the product's own in-dealership assistant. The suite covers the four qualities the task names, with hard compliance checks: lead data must never be sent to a model, one dealership's data must never reach another's user, contact fields must not leave the trusted side, and the conversation must not write business data.

Two configurations were used. First the real AI service with no provider key, which returned 503 to all 21 internal calls and produced the genuine degraded path. Then a recording stand-in on the same port, so the model payload could be captured and a deliberately misbehaving reply could be fed back. The stand-in is an instrument, not a model: it makes no accuracy claim.

Across roughly thirty questions, no forbidden value ever appeared at either inspection point — not the lead-note canary, not either dealership's phone, email or address, not the rival vehicle's VIN. The payload's resource objects carry exactly four keys, so a contact field cannot travel in one.

Two more findings

  • Counting questions never reach the model. Asking how many vehicles are in stock returned a true total of six computed from all matching rows, with the links still capped at five, a sentence generated from a template — and no payload recorded at all. The response still reported a summary as available, so that flag does not mean the model answered. It also means consistency can be asserted strictly for this class of question, which the suite had explicitly ruled out.
  • The degraded path follows the API contract, not the older design note. A real 503 produced a 200 with a null summary and the cards intact. The sentence the older document requires appears nowhere in the response; the wording is a front-end concern. This is also the one case the existing browser suite cannot cover honestly, because it forces the unavailable flag onto an otherwise successful response rather than taking the model down.

The fixture could not be built as designed

Two of the three VINs the suite specifies cannot exist in this product, because a VIN decode is checked against the entered make and model:

1HGCM82633A004352  as "Toyota Camry"    →  400   the VIN decodes to "HONDA"
4T1B11HK0KU000002  as "Toyota RAV4"     →  400   the VIN decodes to "Camry"
2T1BURHE0JC000001  as "Toyota Corolla"  →  201   valid: Toyota, and position 10 is 2018

The VINs are plausible-looking and were never checked against the rule that validates them. The run substituted the project's own convention for test VINs and recorded the mapping. A customer field name was wrong in the same way.

What this task does not cover

No language model was ever invoked, because no provider key was available. Compliance, the handling of unclear input, and the consistency of core-generated answers are covered; the correctness of a model's explanation is not. The report states this rather than filling the cells.

AI-generated automated tests

Differential testing · three oracles, four runs

Verdict
Oracle was wrong

The model was asked for one xUnit file covering a single validation rule: the username accepted by the registration endpoint. It produced 41 tests, and all 41 passed on the first run. That result is worthless on its own, and the interesting work was proving why.

The corrected oracle reads the validation attributes the product actually declares and applies them, so the test file holds no copy of the pattern. Twelve live requests then confirmed the product is fine: every malformed username is rejected with 400 and the message text in fieldErrors.username matches the attribute character for character.

One real disagreement survived. The generated answer claims a whitespace-only username produces two messages. At the attribute level it does. At the API level only the first is visible, because the response envelope keeps one message per field — so an assertion written against attribute metadata cannot predict what the client sees.

The runner project is coursework: it sits outside the product solution, holds one project reference so the tests can read the real DTO, and changes no product file.

Conclusion

What the five tasks have in common

Four of the six defects found were in the tests, not in the product: two impossible fixture VINs, a wrong oracle, a case-sensitivity expectation, and two whitespace partitions argued from the requirement text alone. Each was produced by careful reading and survived a careful review. Each was caught by running the thing.

The product held up. Across every executed case, no tenancy boundary leaked, no question wrote business data, and no validation rule behaved differently from its contract. The two behaviours worth raising — that model prose is passed through unfiltered, and that counting questions never reach the model — are unstated rather than wrong, and both are now written down.

All work was carried out on the project's private end-to-end stack against a throwaway database. No product source file, existing specification, design document or configuration file was modified.
