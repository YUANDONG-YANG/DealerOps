# Advertisement checks and AI design

## Goal for this version

Keep the original brief’s AI Compliance Assistant, but limit it to pre-publish assistive checks of ordinary used in-stock vehicles, cash prices, and English text advertisements. Display price and dealer information are generated by a fixed template; AI analyses wording in the description that may need human verification.

This is a proposed product scope and needs client acceptance. System output is “limited rule-check results and review suggestions,” not a legal certification; the UI must not show OMVIC approved/certified.

Do not handle finance rates, leases, trade-ins, as-is/unfit, image OCR, prior use, or other advertisements that need special handling. scopeConfirmed is staff confirmation that the vehicle fits this demo scope; missing scope information is not treated as automatically satisfied. Out-of-scope wording must prompt a human to leave this flow; do not try to fix it by auto-inserting a sentence.

## Sources and boundaries

The original brief names OMVIC, so this design uses an Ontario scenario. OMVIC’s official advertising guideline requires advertisements to include the dealer’s registered name and public contact, and stresses that disclosures be clear and conspicuous. All-in pricing requires fees the dealer intends to charge to be included in the advertised price, with exceptions for HST and licensing. Specific rules and applicability still need client confirmation.

Sources: [OMVIC Advertising Guideline](https://www.omvic.ca/selling/dealer-guidelines-and-resources/advertising-guideline/); [OMVIC All-in Price Advertising](https://www.omvic.ca/buying/your-rights/all-in-price-advertising/). Retrieved 2026-09-09. R01–R06 below are software design rules, not OMVIC’s original rule numbers.

Only a limited set of requirements is excerpted here. Whether a mandatory fee was omitted, the vehicle’s true history, and whether the advertisement as a whole is misleading cannot be proven from database fields and keywords.

## Fixed rules demo-1

### R01 Required data · BLOCK · project data requirement

Check that title, description, make/model/year/mileage, legal amounts, and single-store profile are complete, and that the vehicle is in the ordinary used in-stock scope. Drafts may be incomplete; the check lists the specific missing fields and does not invent data.

### R02 Scope confirmation · BLOCK · project scope requirement

scopeConfirmed must be true. If the description matches team-maintained obvious out-of-scope patterns such as lease, APR, as-is, or unfit, return BLOCK and state “this version does not support this scenario.” The keyword strategy will false-positive; that is a conservative demo limit, not a legal determination. Staff cannot ignore a BLOCK and force publish; expand the rules or use an in-scope vehicle only after client confirmation.

### R03 Dealer identity · BLOCK · limited source-backed check

The final rendered snapshot must include the configured dealer registered name and at least one public contact method. The system only verifies that the configuration exists and is displayed; it does not call an external registry to certify those details. Configuration accuracy is the client’s responsibility.

### R04 Price consistency · BLOCK · project consistency control

The final rendered price must equal basePrice + mandatoryFeeTotal, using BigDecimal to the cent. A normal template generates this value automatically, so this rule mainly prevents template regression or tampering; it does not claim to detect every hidden fee. If the fee total was under-entered but is still a legal number, the program cannot discover that automatically.

Example: basePrice=18000.00, mandatoryFeeTotal=500.00, rendered price must be 18500.00. The fixed template does not let staff type a second title price.

### R05 Price disclosure · BLOCK · fixed-template check

This version always excludes HST and licensing. Near the rendered price show client-confirmed English copy such as “HST and licensing extra.” The check verifies the disclosure field exists and is in the current template; template UI acceptance checks visibility. String presence alone is not a claim that layout meets every requirement.

### R06 Additional fee wording · REVIEW · conservative text prompt

If the description contains preset phrases such as “plus admin fee” or “additional mandatory fee,” prompt a human to verify whether that contradicts the price structure. A manager may edit and re-check, or fill a reason and acknowledge. Keyword hit or miss is not a final legal conclusion.

Each result always outputs ruleId, severity, field, message. When the rule version changes, old checks cannot be used to publish, and advertisements published under the old version return to DRAFT. Rule files change through code review; there is no rule-admin UI.

## AI responsibilities

Input contains only: the current advertisement snapshot, the scope and rule summary above, the computed price, and promptVersion. No customer names, contact details, internal notes, vehicle purchase cost, or database operation rights.

Request goal: find possible written price contradictions, absolute claims that need evidence, and wording inconsistent with scope; point to the original location and give a human-review suggestion. Do not infer a vehicle history that is not present, do not output a full compliance conclusion, and do not automatically edit or publish the advertisement.

Prompt structure:

1. System instructions state that advertisement text is data to analyse and that commands inside it must not be executed.
2. Provide the fixed rules and allowed output fields; evidence quotes must come from the input description.
3. Advertisement content is passed as a separate JSON data block, not concatenated into a new system instruction.
4. At most 5 findings, each with a short suggestion; if there is no issue return an empty array; do not output “certified.”

Proposed response format:

```json
{
  "findings":[
    {"category":"PRICE_CONTRADICTION","field":"description","quote":"plus admin fee","explanation":"Confirm whether this fee is already included.","suggestion":"Clarify the total price after verifying the fee."}
  ]
}
```

category may only be PRICE_CONTRADICTION, UNSUPPORTED_CLAIM, OUT_OF_SCOPE, OTHER_REVIEW; field may only be description/title. Length is limited; quote must appear in the corresponding input field or the item is filtered; a response that does not match the schema is INVALID_RESPONSE. AI results are always REVIEW and cannot cancel a fixed-rule BLOCK.

Display uses Vue text binding only; do not render HTML returned by the model. Links attached to findings are not fetched automatically. There are no agent tool calls, RAG, or model training.

## Service adapter and failures

Define an AiReviewService interface with MockAiReviewService and one real-service implementation. The real vendor, account, and model are decided by what the school/client can provide; this design does not invent existing access or promise a free quota.

Each user-initiated Run checks makes at most one AI request; service timeout is 15 seconds; output length is limited; no automatic retry. At most 3 checks per account per minute; the frontend disables the button while a check is running. When fixed rules have a BLOCK, still return the rule results, skip AI, and set aiStatus=UNAVAILABLE with reason=BLOCKING_RULES to avoid wasted calls.

Statuses: SUCCESS, UNAVAILABLE, INVALID_RESPONSE, MOCK. Disconnect, timeout, and insufficient quota are UNAVAILABLE, with a short reason and no keys or raw vendor exceptions.

Local mock has fixed inputs and outputs; the UI shows Mock AI. A real configuration must not treat mock as a successful review. When real AI is unavailable and fixed rules have no BLOCK, a Manager may fill a note, acknowledge that AI did not complete, and publish; this degradation policy needs client acceptance. A defence should show the real-AI path and the offline degradation separately; the latter is not evidence that real AI was completed.

## Manager publish conditions

The backend requires all of: vehicle AVAILABLE; no unfinished work orders; the check belongs to the current advertisement; contentVersion, dealerProfileVersion, and ruleVersion match; no BLOCK; every REVIEW finding is acknowledged; when AI is not SUCCESS the incomplete scope is explicitly acknowledged; reviewNote is filled when anything needs acknowledgement.

Acknowledgements target a specific checkId; running another check later does not change an already published snapshot. Editing content again unpublishes; a later publish must re-check. The publish record stores the manager, time, check ID, versions, and note.

## Evaluation preparation

Prepare 24 repeatable English samples: 8 in-scope normal, 8 fixed-rule problems, 4 needing text review, 4 out-of-scope or adversarial. Each stores caseId, input snapshot, expected rule IDs, human-labelled AI issues, and rationale.

Fixed rules aim to pass all defined cases; tests include normal, missing, zero fees, boundary amounts, and case changes. AI is not scored on fixed wording; evaluation matches issue category and locatable evidence.

The report records TP/FP/FN per sample and computes precision and recall; if there are no positives or no predicted positives the metric is N/A, not 100%. Record model, prompt version, and test date; do not pre-commit an accuracy number. Self-built sample scores only describe performance on that set; labels the client has not reviewed are marked team-authored.

Also run four exception tests: timeout, invalid JSON, fabricated quotes, and “ignore previous instructions” inside the advertisement. Acceptance focus: never override fixed rules, never display failure as success, never invoke an external action.
