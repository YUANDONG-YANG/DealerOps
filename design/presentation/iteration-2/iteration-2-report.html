02 Inventory, the sale and sales reporting

This section covers CR-001 to CR-005 (sale visibility and sales reporting), CR-029 to CR-035 (inventory search, filters and form) and CR-047 to CR-050 (VIN and Carfax validation, and the buyer of a sale). A sale is now one transaction that records the seller and buyer, closes the vehicle's leads and writes the audit rows. The work is in the .NET 10 backend (DealerOps.Core, Vehicle module) and the React pages DmsPage, DashboardPage and SalesFunnelPage. The gateway and the AI service are unchanged, and the browser still reaches everything through dealer-gateway.

Terms: DMS is the dealer management system (the inventory screens), CRM is customer relationship management (customers and leads), VIN is the vehicle identification number, Carfax is a vehicle history report service, and vPIC is the public US vehicle-data service that decodes a VIN.

What iteration 1 left missing

In iteration 1 a sale was a status change. A vehicle became SOLD with a date and price, but the inventory did not say who sold it or to whom. The sell dialog showed nothing about what the car had cost the dealership, and a sale could be saved with no buyer. Leads still open on the car stayed open.

The sales report gave all-time and monthly totals and no per-salesperson figures. Inventory search could not find a stock number, and a VIN could be saved against a make, model or year it does not belong to.

The sell transaction

VehicleService.Sell runs as a single transaction. It validates the request, records who sold the car, links the buyer, closes the leads and writes the audit trail together, so inventory, CRM and report agree.

Who sold it, and to whom

Sold by. A new column vehicle.sold_by stores the acting username, taken from the authenticated tenant context, never from the request body. The column is added by the existing start-up migration code in DealerOps.Core/Program.cs.

Sales made before the change had no value, so the per-salesperson rows would have disagreed with the headline totals. The same migration therefore backfills sold_by for SOLD vehicles from the most recent VEHICLE/SELL audit row (actor_username). The sale already wrote that row, so nothing is guessed. A sold vehicle with no SELL audit row stays blank and is left out of the salesperson breakdown.

Sold to. Decision D8 makes the buyer mandatory: either buyerCustomerId (a customer of this dealership) or "Other" with a typed buyerName (up to 120 characters, stored as sold_to_name). A bill of sale needs a buyer, and the CRM link keeps purchase history visible on the customer record. A CRM buyer is linked to the vehicle inside the same transaction, which replaces the separate link call.

A vehicle has one owner link, so a car already linked to a different customer is refused with 409 VEHICLE_ALREADY_LINKED. The typed name is not copied into the audit log, which only records soldToName: true. The Sold to column shows the linked customer name, else the typed name.

Sell dialog: cost, work-order spend, list price

DmsPage loads the vehicle with vehiclesApi.get before opening the dialog and shows Cost (purchaseCost), Work-order spend (repairCost) and List price read-only above the date, price and buyer fields. repairCost is the stored running total: when a work order is completed, WorkOrderService.Patch calls VehicleService.AddRepairCost. Open work orders still block the sale (409 WORK_ORDERS_OPEN), so the figure is final when the dialog is used. repairCost can also be typed on the vehicle form, so it is a stored total and not a live sum of work-order rows.

Closing the vehicle's leads

CloseLeadsForSale finds every lead on the vehicle that is not already Won or Lost. Leads belonging to the buyer customer become WON; all others become LOST with the reason "Vehicle sold". Each change writes a LEAD/UPDATE audit row. This clears dead follow-ups from the CRM and keeps the Won/Lost counts used in reporting accurate.

Sales reporting

GET /api/v1/vehicles/report/sales accepts an optional period of TODAY, WEEK, MONTH or YEAR. Periods are calendar periods ending today on the UTC date; the week starts on Monday. With a period the response adds a period block (from, to, soldCount, revenue, grossProfit). Without one, period is null and the original all-time and monthly figures are unchanged.

The Sales Funnel report page and the dashboard Sales section share one period selector (default Month) and call the same endpoint, so both screens show the same numbers.

The response also carries salespeople: one row per active dealership member, plus any former member recorded as soldBy in the period (flagged activeMember: false). Each row has sold count, revenue, gross profit, current open leads, and leads last updated as Won in the period. Sales are attributed through sold_by, which is why the backfill above matters. Rows are ordered by revenue, then name. Gross profit is sold price minus purchase cost and repair cost.

DMS search, filters and the add-vehicle form

  • Search. The existing q parameter now also matches stockNumber, so no second Stock # box was added. The Make and Model boxes were removed because q already matches make and model.
  • Year. The Year filter is a typeable number sent as the exact modelYear parameter.
  • Open work orders. A checkbox sends openWorkOrdersOnly=true. The server uses the same count as the openWorkOrders column (work orders in OPEN or IN_PROGRESS).
  • Sorting. The list accepts sort=field,asc|desc, applied before paging so all pages are ordered, with blanks last.
  • Form. VIN is the first field. Make is split into "Popular makes" and "All makes". The model-year list shows production years for a fixed set of common make/model pairs and the full list for every other pair (decision D6: a static list for common vehicles only, to stay within the minimum-spec scope).

VIN and Carfax validation

VIN must match the vehicle (CR-047, decision D9). The first approach only compared the VIN's 10th character with the model year, which left the requirement partly met. On create, and on edit when vin, make, model or modelYear changes, the server now decodes the VIN through the existing vPIC catalog client and compares the decoded make, model and year with the values being saved. A mismatch returns 400 VALIDATION with a readable message under fieldErrors.make, fieldErrors.model or fieldErrors.modelYear. Make and model are compared on letters and digits only, so "Mercedes Benz" matches "Mercedes-Benz", and a field the decoder leaves blank is skipped.

Decoder outage. vPIC is an external service, and an outage must not stop a dealership adding stock. If vPIC is unreachable, times out (5 seconds), returns malformed data or does not know the VIN, the server logs a warning and falls back to the older model-year check. The write endpoints therefore never return CATALOG_UNAVAILABLE. During an outage a mismatched make or model can be saved. The add-vehicle form's existing Decode button already fills make, model and year, so those three fields stand for "the vehicle information".

Carfax link (CR-048). A non-empty Carfax URL must be https on carfax.com or carfax.ca (or a subdomain), checked only when the URL changes so older records stay editable.

Known gap. CR-048 also asked for the Carfax URL to be exclusive. The implementation check marks it partial: the host rule is enforced, but the same URL can be used on more than one vehicle, and a blank URL still saves.

API and contract changes

The changes are additive and documented in design/14-Backend-API-Contract.md (§4.2 to §4.5), so existing callers keep working. The exception is that sell now requires a buyer.

Where the logic lives

Business rules sit in DealerOps.Core, which owns persistence and tenancy (each dealership's data kept separate). The UI is a form over the one sell transaction. Storing sold_by on the vehicle lets reporting use a simple query instead of a join into the audit log, which was read once to backfill history. The change reuses the existing q search, the existing vPIC client and one shared report endpoint, so no parallel implementation was added.

03 Roles, team and account administration

This section covers the new Owner role, how people join a dealership, and what the platform admin can still do to accounts. The point to remember: the platform admin no longer adds people to a dealership that already has an owner.

Problem and decision

Before this iteration a dealership had one in-dealership tier above sales staff, MANAGER. The client asked for an "admin / owner / regional manager" who runs one dealership, and for the platform administrator to stop reaching into dealership data. The change document called the role optional and flagged it for discussion. The decision (requirements/iteration-2/CR-Role-Hierarchy-2026-11-03.md, replacing decision D5) kept it narrow: all three names mean one Owner role, no cross-dealership regional manager is built, and the dealership gains a third tier.

Three-tier dealership role

DealerRole is now { Owner, Manager, Sales }, stored on membership.dealer_role as OWNER, MANAGER and SALES (EnumSnakeCaseConverter upper-cases what it writes). The JWT roles are unchanged, still Platform.Admin and Dealer.User, so the gateway role gate and the token format stay as they were.

Core, which owns authorization and tenancy, enforces every in-dealership difference. TenantGuard.RequireManager was split into RequireOwner (dealership profile, join requests) and RequireTeamAccess (owner or manager: Team page, dealership audit log). Each dealership has exactly one active owner.

The two upper tiers differ in three powers: the dealership profile, join requests and acting on managers. Without those the roles would collapse back into the old single manager. Business data is not partitioned. All three roles see the same dealership data, and the sales report counts anyone who sold a vehicle, whatever their role.

Appointment rules

  • First owner: only the platform admin appoints it, by binding an account directly.
  • Owner transfer: the platform admin keeps SetRole (PUT /api/v1/admin/dealers/{id}/members/{username}/role). Setting OWNER demotes the sitting owner to MANAGER and promotes the target in one transaction, with an audit row for both memberships.
  • Last-owner protection: demoting, unbinding or deleting the only active owner is refused with 409 LAST_OWNER (RequireOwnerRemains in MembershipService), so a successor must be named first. If the owner is also the last active member, removal is allowed and the next admin bind creates a new owner.
  • Manager scope: a manager acts on sales members only (promote to manager; edit full name and phone). A manager cannot touch the owner or another manager, and nobody changes their own role.

Join requests replace the direct admin bind

Problem. The platform admin could bind any account straight into any dealership, so an administrator outside the business could add people to dealership data. Solution. Once a dealership has an active owner, the admin can only file a join request on the account's behalf, and the owner approves it. This extends the existing Google self-service request (JoinRequestService, AppUser.RequestedDealerId), so both routes end in the same owner decision. Approval always creates a SALES membership.

Bootstrap exception. An empty dealership has nobody to approve a request. While there is no active owner, MembershipService.AddMember binds the account directly as OWNER. It first takes SELECT ... FOR UPDATE on the dealer row inside the transaction, so two simultaneous binds cannot both see "no owner" and create two owners.

Pending and History

The owner's Team page (TeamPage.tsx) reads join requests from the notifications inbox (GET /api/v1/dealer/notifications?includeResolved=true) and splits them into two tables. Pending lists unresolved requests with Approve and Reject buttons and is always shown in full. History lists resolved ones (Approved, Rejected and cancelled) and pages.

Approval writes the membership, the account binding and their audit rows, and resolves the notification, all in one transaction, so the inbox cannot disagree with the data. Join-request notifications are hidden from everyone except the owner.

One-time data patch

The schema is owned by EnsureCreated plus an idempotent DDL list in backend/dotnet/DealerOps.Core/Program.cs, so renaming roles needed a data patch there. It runs five steps:

  1. Upper-case every dealer_role to the canonical spelling, which also makes later comparisons independent of column collation.
  2. Map any unknown legacy value (such as staff) to SALES.
  3. For each dealership with no active owner, promote the earliest active manager to OWNER.
  4. For each dealership still without an owner or manager but with active members, promote the earliest active member, so every dealership has someone who can open Team and approve requests.
  5. Backfill the new vehicle.sold_by from the latest VEHICLE/SELL audit event, so the per-salesperson sales report adds up to its totals on historical sales.
The patch must run once. Steps 3 and 4 overwrite roles an administrator may have set since. Running them on every restart would promote the earliest manager after an owner was unbound for replacement. The patch therefore claims the id dealer_role_hierarchy_2026_11_03 in a schema_patch (patch_id, applied_at) table with INSERT IGNORE and runs only if that insert claimed the row. The marker and all five statements share one transaction, so a transient MySQL failure rolls the marker back and leaves no half-migrated data. Revert note: restoring old data also requires deleting the marker row. Otherwise a roll-forward skips the migration and the new build cannot parse the old spellings (deploy/ROLE-MIGRATION-2026-11-03.md section 5). Take a fresh backup before the first start with this patch, because the rename cannot be reversed without loss.

Account administration changes

  • Full name no longer unique. People share names, and sign-in is identified by username and email. The DDL patch list drops the unique index uk_app_user_display_name (ALTER TABLE app_user DROP INDEX) and the DISPLAY_NAME_TAKEN check was removed with it. The UI label now reads "Full name".
  • Soft delete with typed confirmation. The admin can delete a dealership and delete a member account (DELETE .../members/{username}/account). For a dealership, DealerAdminService sets deleted_at, marks it inactive, softly unbinds its members and clears pending requests to it. Vehicles, sales, customers and audit rows are kept for history. In AdminPage.tsx the dialog enables its button only after the admin types the dealership legal name or the account username exactly, which guards against a click on the wrong row.
  • Pending accounts are editable. The admin's Pending accounts view (PendingAccounts component) can edit an unbound account's username, email and phone (at least one of email or phone is required) or delete it, so a typo at registration no longer needs a new account.

Scope boundary

The decision of 2026-11-03 was to meet the change document and no more. The owner edits a member's full name and phone and nothing further. These powers stay with the platform admin:

Widening this table requires a client discussion first, as the change document states. Design references: design/15-Data-Auth-and-Gateway.md sections 2.5 and 8, and design/14-Backend-API-Contract.md section 3.7b.

04 Leads, CRM and the audit log

This section covers three areas that sales staff and managers use daily: lead lifecycle, customer records (CRM) and the audit log. The old behavior let data contradict itself, with two open leads for one car or a Won lead that no longer matched a recorded sale. It also slowed routine work, with dropdowns where a search was needed and an audit log filtered only by exact text. The logic lives in DealerOps.Core, and the React pages reach it only through the gateway.

4.1 Lead lifecycle rules (decision D7)

Problem. A Won or Lost lead was final, the same customer could hold several open leads for one vehicle, and selling a vehicle left every other lead on it open. In each case the pipeline disagreed with the stock list.

Solution. Decision D7 in requirements/iteration-2/CR-Analysis-2026-11-03.md sets the rules below. LeadService (backend/dotnet/DealerOps.Core/Lead) enforces them on the server, so no screen can bypass them.

RuleMechanism
A Lost lead can always be reopenedLeadService.Reopen accepts New, Contacted or Qualified as the target, clears LostReason, and writes an UPDATE audit row flagged reopened. It still requires the lead's vehicle to be in stock, because an open lead on a sold vehicle is a state that creation already forbids.
A Won lead can be reopened only if its vehicle was not sold to that lead's customerSoldToLeadCustomer checks for a Sold vehicle linked to the same customer through CustomerVehicles. If true, reopen fails with LEAD_CLOSED, because a reopened Won lead would contradict a recorded sale.
One open lead per customer and vehicleRequireNoOpenDuplicate runs on create, on changing a lead's vehicle, and on reopen, and raises LEAD_DUPLICATE. A lead with no vehicle is never a duplicate, and a closed lead does not block a new one.
A sale closes the vehicle's open leadsVehicleService.CloseLeadsForSale, in the same transaction as the sale: the buyer's lead becomes Won, every other open lead becomes Lost with the reason "Vehicle sold". Each change is written to the audit log, and the matching website-inquiry inbox messages are resolved.
A repeat website inquiry adds a note, not a leadBuyerSiteService.Inquire looks for an open lead for the matched customer and vehicle. If one exists the inquiry text is written as a LeadNoteEntity on it; otherwise a New lead is created and only then is the BUYER_INQUIRY inbox message sent.

4.2 Lead screen usability

Problem. Staff had to pick a customer and a vehicle from long dropdowns, set the owner by hand every time, and could not find a lead by car.

Problem. Closing a form by accident lost typed data, and two high-impact actions, editing the dealership profile and closing a lead, saved with one click.

Confirm before save

4.6 Why it is built this way

Lifecycle rules sit in the services because the same lead can be changed from the Leads page, the sale flow and the public buyer site, and a rule held in one screen would leave the others free to break it. A duplicate customer is a warning because dealerships have legitimate repeats. A duplicate open lead is an error because it is never legitimate. The two audit logs share one panel and one query so they cannot drift apart.

5.3 The sorting contract

The client asked for sortable columns on the DMS, Leads, Team, Admin and audit tables. Before iteration 2 no list accepted a sort and the table component had no sort support. The rule: a paged list sorts on the server, an unpaged list sorts in the browser.

Paged lists: the server sorts

The list endpoint takes sort=field,asc|desc. Paging.ParseSort checks the field against a whitelist for that list and returns a 400 VALIDATION on sort for an unknown field or direction. The query is ordered before paging, and columns that can be blank use OrderByDirectionBlanksLast so empty values stay at the bottom in both directions. The frontend builds the value with sortParam() and reloads the page when a header is clicked.

Unpaged lists: the client sorts

When every row is already loaded, useSort in TableSort.tsx sorts a copy of the rows in the browser. Blank values go last, numbers compare numerically, and text compares case-insensitively with embedded numbers in order. DataTable itself never sorts; it renders what the caller passes and reports header clicks through onSort.

Why sorting only the current page fails

A header on a table that shows 10 of several hundred rows suggests "this column, ordered". If only the visible 10 are reordered, the first row is not the highest value overall, and a user can believe a record is missing because it sits on page 4. For a paged list the order must be decided before the page is cut, so only the server can do it.

Dealership and user administration

CR-060 Delete a dealership Done

Client said
Changes: Dealerships should be able to be deleted by platform admin; however, this should be a more complex decision requiring at least one extra step to confirm.
Our reading
Platform admin may remove a dealership, guarded by an extra confirmation. Hard versus soft delete was not stated, so history is kept (decision D6).
What we did
The Dealerships table in AdminPage has a Delete action that opens a ConfirmDialog; the button stays disabled until the dealership's legal name is typed. It calls DELETE /api/v1/admin/dealers/{id} (DealerAdminService.Delete, platform admin only), which soft-deletes the dealership, unbinds active members and removes it from the admin list and the public shop directory.
Why it solves the problem
Dealerships that should no longer exist can be removed, and the typed-name step prevents accidental deletion.

Done; the action is on the Dealerships row beside Edit, not inside the Edit drawer, and vehicles, sales and audit history are kept.
