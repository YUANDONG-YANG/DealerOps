Project goal and who it serves

DealerOps is a multi-tenant web platform for independent used-car dealerships in Ontario. It joins three modules over one backend and one database: DMS (vehicle inventory and sale), CRM (customers and their purchased vehicles) and advertising compliance (a check of an ad against OMVIC rules (the Ontario motor vehicle dealer regulator) before it may be marked Ready and exported as TXT), plus a read-only AI assistant for in-dealership questions. A small dealership otherwise keeps inventory, customers and advertising checks in separate places, and an ad that omits a required disclosure or shows a stale price can breach Ontario advertising rules.

Platform administrator

One platform-wide account (Platform.Admin). Opens dealerships and binds staff. Holds no business data; vehicle APIs reject it.

Dealership users

Dealer.User, each belonging to exactly one dealership. All users of a dealership share that dealership’s data and no other’s.

02 Core business: tenancy, DMS, CRM, audit

Several dealerships share one deployment and one database, and DealerOps.Core shows each of them only its own vehicles (DMS, the dealer management system), customers (CRM, customer relationship management) and history (audit). Remember the two-layer rule: every important check exists once in a service and once in the database. The requirement IDs (AUTH, DMS, CRM, AUD) refer to requirements/iteration-1/DealerOps-Requirements.md.

1. Multi-tenant isolation

Problem

Dealerships are competitors. If one staff member could read, guess or even detect another dealership's vehicle or customer, the product would be unusable. A browser-supplied dealerId cannot be trusted, and a forgotten WHERE clause in a single query would leak data.

Solution

The server alone decides the dealership, from the signed-in identity (AUTH-09). The service layer and the database context each enforce isolation, so a single mistake cannot leak data.

How it works

  • Identity to tenant. The gateway validates the JWT; TenantMiddleware in Core then loads the caller's single active membership and binds the dealership id to the request (TenantContext, AppDbContext.SetTenantDealerId). Any dealerId sent by a client is ignored.
  • Role gates. TenantGuard exposes RequireDealerUser, RequireTenantId, RequireTeamAccess (owner or manager), RequireOwner and RequireAdmin. Every business service starts with TenantGuard.RequireTenantId(). A wrong role, an unbound user or the platform admin gets 403 FORBIDDEN and no business fields (AUTH-08).
  • Global query filters. In AppDbContext.ApplyTenantFilters, vehicles, customers, customer-vehicle links, listings, ad checks, leads, work orders, photos and payments all carry a filter of the form tenantDealerId != null AND DealerId == tenantDealerId (plus DeletedAt == null for soft-deleted tables). A request with no dealership reads nothing. New rows receive the caller's dealership automatically in AutoAssignTenantId on save.
  • 404, not 403, across tenants. A record id that belongs to another dealership is reported as 404 NOT_FOUND (AUTH-07), through the filter itself or through TenantGuard.AssertSameDealer. A 403 would confirm that the id exists. The real dealership ids are written only to the operator log.
Admin boundary. The platform admin manages dealerships and logins but has no access to business data (AUTH-01, AUTH-08). The same guard enforces this rule and the dealer rules, so there is one place to review. The 403/404 matrix is in design/15-Data-Auth-and-Gateway.md.

2. Vehicle inventory (DMS)

What a vehicle is

A vehicle (VehicleEntity) holds the eight required intake fields (VIN, make, model, model year, source, purchase cost, date added, condition) and optional extras such as repair cost, Carfax URL, mileage, colour, fuel type, stock number and list price. Sale data (SoldOn, SoldPrice, SoldBy, buyer) is kept apart and written only by the sell action. Money accepts at most two decimals and is refused rather than rounded (MoneyRules.RequireCents). Deletion is soft (DeletedAt).

VIN uniqueness per dealership

The VIN is upper-cased and validated, and the database holds a unique index uk_vehicle_vin on (DealerId, Vin). Two dealerships may therefore stock the same VIN (DMS-03), but a duplicate inside one dealership returns VIN_DUP. The pre-check uses IgnoreQueryFilters so that a soft-deleted vehicle still blocks reuse, and the index is the final guard against two simultaneous requests.

The sold pair and the sold lock

  • Sold pair (DMS-10). Sold date and sold price must arrive together and the price must be above zero; otherwise SOLD_PAIR_REQUIRED. Sold date cannot be before the date added or in the future.
  • Sold lock. Once Status is SOLD, any edit that changes a purchase or descriptive field (make, model, year, VIN, source, costs, mileage, stock number, list price and the others) is rejected with SOLD_LOCKED (HTTP 409). A sold vehicle cannot be sold again, unlinked from its buyer or deleted. A sale is also blocked while work orders are open (WORK_ORDERS_OPEN).

Optimistic locking

Two staff members can open the same vehicle. Each edit or sell request carries the version it was loaded with. VehicleService compares it with the stored value and returns VERSION_CONFLICT if someone saved in between, and the second user reloads instead of overwriting the first save. The entity field is guarded by [ConcurrencyCheck], and AppDbContext.BumpVersions increments it on every modified row at save time, because EF Core does not do that by itself. Customers use the same mechanism.

3. Customers and the vehicle link (CRM)

A customer has four required fields (name, email, phone, home address) and a detail view showing linked vehicles and history. The link between customer and vehicle (customer_vehicle) follows these rules:

  • One vehicle, one customer. The unique index uk_cv_active_vehicle on the active-link column enforces it in the database. A second customer linking the same vehicle gets VEHICLE_ALREADY_LINKED; the sell path also catches the duplicate-key race and reports the same code.
  • Link candidates. Only vehicles of the same dealership that are not already linked may be linked, in stock or sold (CRM-05, CRM-06). A customer or vehicle id from another dealership is 404, as is unlinking a link that does not exist (CRM-09).
  • Sold link is permanent. An in-stock vehicle can be unlinked; a sold one returns SOLD_LOCKED. Likewise the buyer of a sold vehicle cannot be deleted.
  • Selling to a customer. The sell dialog names a CRM customer (which creates the link in the same transaction) or "Other" with a typed name. Free-text buyer names are never copied into the audit trail.
  • PII boundary (CRM-12). A customer's phone, email and address never reach AI prompts, application logs or assistant answers. The audit trail is the one exception: it stores contact values (AUD-04) so that every version of a customer is traceable, and only managers and the admin can read it.

4. Audit trail

Problem and approach

A dealership must be able to answer "who changed this vehicle's price, and what was it before?". For that the audit trail is append-only (AUD-05): AuditService.Record only adds a row to AuditEvents; no update or delete path exists in the service.

Same transaction (AUD-07)

Record does not save by itself. It adds the audit row to the same AppDbContext as the business change, so one SaveChanges writes both. If the business change fails, no audit row survives; if the audit row cannot be written, the business change rolls back. Multi-step operations such as sell open an explicit transaction around all steps.

03 OMVIC ad compliance and the AI layer

This section covers how a vehicle ad is checked before it can be published. Deterministic rules decide whether an ad passes; the AI model can only add notes.

The problem

Ontario dealerships must follow advertising rules set by OMVIC (the Ontario Motor Vehicle Industry Council): a vehicle ad needs a price, the dealer's legal name and contact details, an honest condition statement, and, when it quotes financing or a lease, the APR, term and related figures. Missing one of these is an objective failure. Whether the wording is misleading is a judgement call. A single AI prompt for both jobs would be unreliable on the first and unexplainable on the second, and it would send dealer data to an external model on every keystroke.

A two-layer check

Iteration 1 splits the check into two layers. A rule engine (OmvicRuleEngine in DealerOps.Core) runs first and can block. Only if no rule blocks does Core call the separate DealerOps.AiService for a second-pass review that can only add advisory notes. A listing can be marked READY or exported as TXT only when its latest check passed and that check still matches the current content.

Why deterministic rules run first

  • Objective gaps have one right answer. "Is the price in the ad?" is settled by regular expressions and fact comparisons, which give the same result every time and trace to a rule code.
  • Only rules may block. A model cannot veto an ad. The AI system prompt states that notes are REVIEW or INFO only, and the adapter coerces any other severity to REVIEW.
  • Cost and privacy. A listing with a BLOCK finding never leaves Core, so the model is called only for ads that are already structurally complete.
  • Dealer-tunable. ComplianceRuleService stores per-rule overrides (enabled, severity, message). The engine output is filtered through them before the block decision, so rules can change without a deploy.

Rules are grouped by what the ad claims. Each finding carries a code and a severity: BLOCK stops the ad, REVIEW asks a human to look. BLOCK findings are listed before REVIEW findings.

Content-version invalidation

Each listing has an integer ContentVersion, separate from the optimistic-lock Version. Each stored check records the content version it evaluated. The version is bumped when:

  • a listing edit really changes a field (ListingService; re-saving identical text does not turn a PASSED ad into STALE), and the listing is also reset to Draft;
  • a vehicle's conditionCode changes (VehicleService), because the condition rules depend on it;
  • the dealership changes its compliance rule settings (ComplianceRuleService bumps every listing's version), so ads are rechecked under the new rules.

The check reads the version before evaluating, so an edit made while the model is running cannot be mistaken for a pass of the new text. A price or condition change therefore voids an old pass with no cleanup job. The buyer site uses the same predicate (ContentVersion equality) to decide which ads are public.

The AI service boundary

Stateless, no database

DealerOps.AiService has no data access. Core sends only public fields (title, body, ad kind, medium, vehicle year/make/model/VIN/condition/source, dealer name and contacts), never purchase cost or customer records.

Fixed time budget

Connect 2 s plus response 13 s, a 15 s total budget enforced by TimedModelCall, capped at 16 concurrent calls. Overload is reported as its own error, not as a timeout.

Failure is never a pass

A timeout, transport error, or a reply with no usable note is stored as UNAVAILABLE and surfaced as the API error AI_UNAVAILABLE. An empty reply counts as failure because it would otherwise look like a clean result.

Notes never veto

The adapter keeps at most 8 notes, 300 characters each, with severity REVIEW or INFO only. Rules decide pass or block; notes inform the person.

Prompt-injection mitigation

Ad copy is typed by dealership users, so it is untrusted. In AdCheckAdapter the title and body are placed between explicit UNTRUSTED_AD_TITLE and UNTRUSTED_AD_BODY markers, after the trusted facts. Any <<< or >>> in the copy is broken up so it cannot close its own block, and input is truncated (300 / 4,000 characters).

The system prompt in SystemPrompts.AdCheck tells the model to treat the marked text purely as data, never obey instructions inside it, and report an attempt to steer the review as a note. The prompt also forbids claiming "OMVIC approved" or "legally cleared". A successful injection can still skew the notes, but it cannot make a blocked ad pass, because the model's output is advisory.

TXT export gate and the disclaimer

POST /api/v1/listings/{id}/exports and the READY transition share one guard, AssertExportable. It checks tenant ownership, the optimistic version, and that the latest check is Passed. Otherwise it fails with NOT_PASSED; if the content has changed since, it fails with CHECK_STALE. The export holds only public content: the dealer's four public fields, vehicle year/make/model/VIN/condition/source, the ad text, and the check time. Cost figures and customer data are left out. It ends with a fixed line: "This check is not legal advice and is not an OMVIC approval. Confirm current disclosure requirements with OMVIC before publishing."

The same statement appears under the check result in the ad workspace and on a dedicated disclaimer page. Each export is audited as EXPORT with the content version that left the system.

The read-only assistant

The assistant (AssistantService in Core, AssistantAdapter in the AI service) answers questions about the dealership's own inventory, customers and ads. The backend retrieves the data and the model only phrases the answer.

  • Tenant-scoped retrieval. Core resolves the tenant from the caller's identity and builds up to five resource cards (AssistantResourceQuery) from that dealership only.
  • Deterministic counts. Questions such as "how many ..." are answered from database counts with no model call, because a model that sees five truncated cards cannot know the total. The system prompt also forbids inferring counts from cards.
  • Minimal data to the model. Core passes only each card's kind, id, label and status to the AI service. The prompt forbids revealing purchase cost or a customer's phone, email, or address, and tells the model to refuse any request to change data.
  • Model outage. If the model is down, AiCallFailed is caught and the response still carries the retrieved cards with no summary. Retrieval has already succeeded, and nothing is written.
  • Card selection. When the summary names ids (for example "#12"), only those cards are returned; otherwise the full retrieval list is shown.
Why rules hold the authority. Rules can be explained and tested. The model covers what rules cannot, such as contradictory or misleading phrasing, and a model outage shows as "check unavailable" while the rest of the product keeps working. The browser never calls the AI service; requests go through the gateway to Core, which owns tenancy, persistence and audit.
Known limit. The rules are pattern-based on English text, so unusual phrasing can be missed or over-flagged. That is why most disclosure rules are REVIEW rather than BLOCK, and why every result carries the not-legal-advice statement.

04 Architecture

Iteration 1 delivered four deployable applications, one MySQL 8 database, synchronous REST between the services, and a stack that Terraform creates on Azure App Service (requirements ARC-01 to ARC-07 in requirements/analysis/05-Cross-Cutting.md). The browser can reach only the Gateway. Core alone owns authentication, tenancy, business rules and the database.

DMS (dealer management system, vehicles), CRM (customer relationship management) and ad compliance are three front-end entries over one back end. The ad check therefore reads vehicle and dealership data directly, with no re-entry (ARC-01, ARC-02).

Stack history. Iteration 1 began on a Java/Spring and Vue stack. On 2026-10-14 the repository was restructured and the Azure deployment moved to a .NET backend with a React frontend (git history); the runtime was later raised to .NET 10. The Java and Vue modules are retired and kept as legacy reference. Service boundaries, endpoints and the data model did not change in the move. This section uses the active names (design/TECHNOLOGY-STACK.md).

Why this shape

The AI service has no database, so a model prompt contains only what Core chose to send, which keeps customer personal data out of AI calls. Authentication stays in Core because a two-role system does not justify a fifth service.

4.2 Request path and security checks

Every check can be traced by following one authenticated call, here GET /api/v1/vehicles. The Gateway checks the token and role. Core checks the internal header, the token again, and the tenant.

Double JWT validation

The Gateway rejects bad tokens at the edge: signature, issuer, audience and expiry with a 30 second clock skew. Core validates the token again because it owns authorization and does not rely on network position. Both use the same HS256 secret (DEV_JWT_SECRET, held in Azure Key Vault as JWT-SIGNING-SECRET).

Internal secret header

INTERNAL_TOKEN is shared by the Gateway, Core and the AI service and travels as X-Dealer-Internal. YARP strips any client copy of the header and adds the real value to the outbound request. The Gateway answers 404 to a browser that sends the header on a public path or requests /internal/** without it, so internal routes are not revealed. Each service refuses to start if the token is the well-known default and the JWT mode is not dev.

Tenant from membership

The JWT states who the user is and whether they are an admin or staff. It does not name a dealership. Core loads the one membership row with active=1 for the username and uses its dealer_id. A dealerId in a body, query or header is ignored. AppDbContext applies query filters on DealerId to vehicles, customers, listings, leads and the other tenant tables, and it hides soft-deleted rows where the table has deleted_at. With no tenant resolved, the filters return no rows.

4.3 Authentication and roles

Users sign in with an email, a username or a phone number plus a password (POST /api/v1/auth/login). Passwords are stored as salted BCrypt hashes, and every failure returns the same 401 message. Self-registration (POST /api/v1/auth/register) creates an unbound account. Google and Firebase ID-token sign-in were added later in the iteration as extra routes into the same account model. Core issues the single HS256 token (sub is the username, roles holds one role); the Gateway and Core only validate it.

Two JWT roles

Platform.Admin manages dealerships, accounts and membership (/admin/**, /me, /auth/**) and sees no business data. Dealer.User works inside one dealership. If a token carries both roles, Admin applies.

Bind and unbind

A new account is unbound and lands on a "no access" page. The platform admin binds it by creating an active membership row. A person has one active dealership, so a second bind returns 409 DUP_MEMBER, and the bind locks the user row to survive concurrent requests. Unbind sets membership.active=0 and clears app_user.dealer_id, and keeps the account, password and audit history.

The role is in the token and the dealership is in the database, so a grant or revocation applies on the next request without reissuing tokens. Differences between owner, manager and sales were added later (iteration 2 change request) as membership.dealer_role. They are not extra JWT roles.

4.5 Synchronous REST and one database

One database. Vehicles, customers and the ad check read each other's data in the same transaction (ARC-02), and a second store would need copies and reconciliation. Only Core connects, so the Gateway and the AI service cannot touch data.

Synchronous REST. The ad check is a request the user waits for. Core runs the deterministic rules first. If no rule blocks, it calls the AI service and waits up to a configured limit (default 16 seconds, AiService:ResponseTimeoutMs). A failure returns 502 AI_UNAVAILABLE with no hidden retry queue, and the page cannot mark the ad ready. Messaging (Service Bus, outbox, dead-letter queues) was out of scope for a four-person team and two sprints (ARC-05).

4.6 Deployment

Infrastructure

Terraform (deploy/terraform, AzureRM provider) creates one resource group with these resources:

  • a Linux App Service plan and four Linux web apps: web, gateway, core, ai;
  • an Azure Database for MySQL Flexible Server that requires TLS;
  • a Key Vault holding the MySQL connection string, JWT signing secret, internal token, admin password and AI key;
  • a user-assigned identity through which the apps read those secrets as Key Vault references, so no app setting holds a secret value;
  • Log Analytics and Application Insights.

Terraform generates the random passwords and tokens, so none appear in source. Core and the AI app also restrict inbound traffic to the Azure service tag. That stops browsers, while the internal header remains the real authorization.

Releases and CI

deploy/terraform/deploy-apps.sh (wrapped by deploy/deploy.sh) publishes the three .NET apps and the React bundle, which App Service serves as static files with SPA fallback. It refuses to run from a dirty checkout or from a commit that is not the latest upstream commit, so all four apps come from the same source. CI lives in .github/workflows/, with one pipeline per service plus terraform.yml. It compiles, validates formatting and schema, and holds no Azure credentials.

Deviations from the original brief. Containers (Docker, Kubernetes) were dropped for App Service packages (SCOPE-BASELINE errata 5). CI validates but does not deploy, so an operator runs each release. In local development Core and the AI service listen on all interfaces, so ARC-03 holds in the cloud and not on a developer machine (design/07-Azure-Microservices-Architecture.md, status of ARC-03 and ARC-07).
