Change A: audit rows keep the actor and dealership as they were

Problem

The platform admin's audit log showed the dealership as a bare id such as 285 and had no role column. audit_event stored only dealer_id and actor_username. Resolving a name at read time would let a later rename or role change rewrite history, so the values have to be stored when the row is written.

What the user sees

In the admin log and the dealership log (opened by an owner or manager) the Actor cell reads lafe (Lafe Smith), a new Role column follows it, and the Dealership cell shows the dealership's legal name. Rows written before the change have no snapshot, so they show the username alone, — as the role and #285 as the dealership. They are not backfilled, because current values would be presented as historical ones.

How it works

  1. Every audit row is written by one method, AuditService.Record, inside the same transaction as the business change. Its signature is unchanged, so no caller was edited.
  2. Before the entity is added, the new private method SnapshotActorAndDealer fills three fields. DealerName comes from _db.Dealers.Find(dealerId)?.LegalName. ActorDisplayName comes from the AppUsers row with the actor's username. ActorRole is PLATFORM_ADMIN when user.Role == AppRole.PlatformAdmin, otherwise the actor's membership role at that dealer_id (EnumWireName.Of(membership.DealerRole)). Active memberships sort first.
  3. The lookups read .Local (entities already tracked in the unit of work) before querying the database. A row written together with a rename or role change therefore records the state that change produced.
  4. If the username matches no AppUsers row (anonymous), all actor fields stay null. If the actor has no membership at the row's dealership, only the role stays null.
  5. On read, PageOfLog copies the stored values into AuditItem (ActorDisplayName, ActorRole, DealerName). Nothing is looked up again. The record-history endpoint does not return the three fields, the same rule already used for dealerId and clientIp.
  6. In the browser, AuditLogRow in api/audit.ts gains the three optional fields and AuditLogPanel.tsx renders them through the gateway as before.

Limits and open points

  • Existing rows keep null snapshots permanently. Old and new rows therefore look different in the same log.
  • actor_role is a membership role, so an actor without a membership at the row's dealership has a null role even though the account exists (for example an unbound account).
  • The snapshot adds up to three small queries per audit row. This is not measured; audit rows are written once per business operation.
  • The Actor and Dealership text filters still work on actorUsername and dealerId. Searching by display name or dealership name is not part of this change.

Change B: custom source name for vehicles (DMS-19)

Problem

A vehicle's source is one of four values (TRADE_IN, AUCTION, PRIVATE_PURCHASE, OTHER). OTHER says nothing about where the car came from, and the inventory list had no source filter. design/21 records the requirement as DMS-19 and attributes it to the client review of 2026-11-09 filed under requirements/iteration-3 (CR-Vehicle-Source-Other-2026-11-09.md).

What the user sees

  • Choosing source Other on the add or edit form shows a required "Other source" box (up to 100 characters, placeholder "Lease return"). Names already used by the dealership appear as suggestions.
  • The inventory list has a Source filter. Picking Other adds a second dropdown with "All other" first, then the dealership's custom names.
  • The Source column reads Other: Lease return when a custom name exists.
  • On a sold vehicle the box is disabled, like the other locked fields.

How it works

  1. Storage. VehicleEntity.SourceOther maps to vehicle.source_other VARCHAR(100) NULL.
  2. Validation. VehicleService.SourceOtherFor returns null for any source except Other. For Other it trims the value and throws ApiException(ErrorCode.Validation) keyed on sourceOther ("Enter the source when Other is selected.") when it is blank. On PATCH, allowBlank is true only if the stored vehicle is already Other with no name, so records saved before DMS-19 stay editable. The browser repeats the rule in validateForm and sends sourceOther: null unless the source is OTHER (vehicleWriteBody).
  3. Audit. Create writes sourceOther into the field summary when present. PATCH records a changed sourceOther with its previous value, and the key counts as a purchase field, so it follows the same rules as source.
  4. Filters. GET /api/v1/vehicles accepts source (exact) and sourceOther (Other vehicles only, compared ignoring case). Both flow through VehicleFilter into VehicleService.List.
  5. Options. The new GET /api/v1/vehicles/source-other-options calls VehicleService.SourceOtherOptions. It reads the caller's tenant only, merges names that differ in case (spelled as on the newest vehicle) and sorts them ignoring case. DmsPage loads the list on mount and again after a save with source Other.

Limits and open points

  • The options endpoint returns every distinct name and has no paging. A dealership with many free-text sources gets a long dropdown.
  • Two spellings that differ beyond case (for example "Lease return" and "Lease-return") stay separate options.
  • The list query lower-cases SourceOther in SQL, which prevents use of an index on that column. This is acceptable at the current data size and is not changed.

Schema patch at startup

Core adds columns to existing databases through the ALTER TABLE list in Program.cs, and EnsureCreated covers new databases. Four statements were added:

StatementEffect on existing data
audit_event ADD COLUMN actor_display_name VARCHAR(120) NULLOld rows get NULL

All four columns are nullable with no default, so no backfill is needed and the statements are cheap on a populated table. They follow the existing pattern used for client_ip and client_location. The cloud database is upgraded the next time the new Core build starts against it. No data is removed or rewritten.
